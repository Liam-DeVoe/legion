# `spec-check state`

`spec-check state --scenario <dir> [--json]` derives the state of each check and approved statement in a scenario. The command reads the same scenario format as `specgraph.ReadScenario`; it does not change the scenario or its expected output.

A scenario contains `approved.json`, `files`, `history.json`, `jobs.json`, `results.json`, `subjects.json`, `ties.json`, and `uncited.json`. It can contain `units.json`; without it, no statement wait is derived. `want.txt` is test data only and is not read by the command.

The command prints one result for every subject. A statement is `met`, `met, partly checked`, `not built`, `not met`, or `unknown`. It then prints every check that reads that subject as `true`, `false`, or `unknown`, including a reason and, for a true or false result, where its counted result came from: the commit for a check of the code, the deploy for a check of production, and the graph transaction for a check of the graph. It prints no list of a check's results with their times. If `units.json` is present, it also prints whether each wait ends or holds. `--json` emits the same derived data as JSON.

Scenario input is strict. Unknown fields, duplicate fields, invalid JSON types, and `null` values are refused rather than silently read as zero values. A missing member follows its declared input mark: some missing values are valid zero values, while members whose absence would hide a fact are refused. Empty objects can be valid values; for example, an empty `uncited.json` says CI refused no check.

A result counts only for the procedure and subject it read. For checks that count at commits, a result carries to another commit only when the check has known ties at both commits and no tied path changed. A result whose current check text, current statement approval, or tied code does not match is not reused.

A program check of code needs a valid failing example before it can be true. The failing example counts from `planted_on`, never from its own `commit`, which is the commit where CI ran the fault. It needs one or more fault paths; every path must be a source file, not a test file, and where the check's tie at `planted_on` is known, that tie must cover every path. A record with no planting commit, no fault path, an all-white-space path, a blank path beside a real path, or `planted_on` equal to its own commit counts nowhere and makes the check unknown with its specific reason when it is the newest candidate. A record whose `planted_on` names no commit of the history also counts nowhere; as the newest candidate it makes the check `unknown (planted_on_outside_history <commit>)`.

A CI refusal at a commit makes its check unknown at that commit. It removes that commit's own results, including a planted failing example whose counted commit is the refused commit, but it does not remove evidence from other commits, and it does not remove a record that counts from no commit, whether CI refused the check at the commit its `planted_on` names or at its own commit.

The scenario sweeps exercise omitted members, nulls, empty names, altered paths, and CI refusals. Each sweep fails an input whose files equal its base's, so a sweep writer that writes nothing fails by name. Each sweep also fails an input whose files are those of an earlier input of the same base, byte for byte, so that it reads no case twice; a sweep writes each JSON file with the members of each object in the order of their names, so two inputs that write one tree hold the same bytes, and a test fails when the encoder writes one tree in two orders. Each sweep also reads back each write against the write it means, which the sweep builds from its own decode of the base before the writer runs: each file by its name, with every other file of the base unchanged and no file added; a JSON file as the base's tree with the one change that the input names (a string or added member, a null, a member or element left out, a renamed key, or a text inside a block), compared whole; a spec file by its bytes; a CI refusal as the scenario reader reads it, by its commit, its check and its rule; the results that such a refusal takes out, as the reader reads them; and each file as its bytes alone, with no mode, time or sys. Each object that a writer gets is its own: a decode of the file made for it alone, a copy of the files, and copies of the place and the value, or of the places of the results that a refusal takes out. So a writer that writes another value, writes it at another place, under another key or under another file name, also changes another part of the file, or makes a file a directory or a link, fails by name too.

Each table that a sweep reads of its own is a function that gives a new value at each call. The sweeps judge what the reader reads in a process of its own. Test code runs in the test process, in the reader's package, so it can name and change what a reader in that process reads: the package's variables, the storage that a regular expression or a string replacer hands out, the scenarios in memory, and the exported values of the libraries that the reader calls. So the reader that the sweeps judge is a main package of its own, `internal/sweepreader` under specgraph, which holds specgraph and the standard library and no test file. Each sweep, the test that takes a whole record out and the test of the sweeps' judgment below each build that binary once, with the overlay that `ENVOY_TEST_GO_OVERLAY` names where a probe lays a fault in the reader, and start processes of it, one for each base of a sweep and one for each of the other two tests, each with the Go runtime's own settings alone: `GOMAXPROCS` as the test process runs with it, and `GOMEMLIMIT`, `GOGC` and `GODEBUG` where the test's environment sets them, so each process runs under the runtime settings of its test and sizes itself to them, not to the machine; no other variable of the test's environment reaches it. The sweep writes each scenario to it as one line, each file by its name and its bytes, and the process answers with one line: the state of each check, statement and wait at each subject, or the refusal. That process shares no memory with the test process: no code of the test process, a test file's `init`, a writer, a cleanup or a goroutine among it, names or changes a value that the process reads, at any time; only the operating system's access of a parent to its child (`ptrace`, `/proc/<pid>/mem`) reaches that memory, and no test uses it. Each base that no scenario holds is built alone, from a read of its scenario of its own, by writers of the package that each get the tree of one file of that base, so no writer of a base can reach another base. Three limits stay. The package's other tests, outside the sweeps, call the reader in the test process, so test code shares its memory: test code that changes a value that the reader reads, at `init`, in a test or in a writer, whether or not it puts the value back, can hide a fault from them. Test code makes each input's bytes and its right, so an input that is wrong from the start is caught only by the checked-in digest and the known positives below, which a change can write again together with the fault. And the test process builds the reader's binary and starts each process of it, so test code that runs before a process starts, before the build or after it, chooses the code that the process runs and the runtime settings above: before the build, a test file's `init` among it, by `ENVOY_TEST_GO_OVERLAY`, `GOFLAGS`, the `go` on `PATH` or a file on disk; after the build, by a write over the binary or by a change of those settings in the environment between two starts. Such code can hide a fault of the reader from the sweeps; only a reader built and started outside the test process would close that.

Each sweep judges each input that it derives: it compares the input's states with those of the base, and an input that moves a state toward true fails unless the input has a right to that move. Of each base, a sweep judges at least a fixed count of inputs that the reader reads and a fixed count that it refuses, and the bytes that the reader read of the base and of each input, with each input's kind, read or refused, its right and the places that the right allows, in their order, have a fixed digest. An input counts only where the sweep judged it and found it right, so a fault that drops inputs, a sweep that skips inputs that it built or drops one from its judgment, and a fault that moves inputs from one kind to the other, as many each way as it likes, each fails by name. The counts hold what the reader did with each input, not what the judgment found, so a judgment that stops reporting an input that moves a state toward true, and counts it as read, would meet them. So the judgment, whether an input's state at one place moved toward true beyond the input's right, is one function (`movedBeyond`, in specgraph's `sweepjudgment_test.go`) of four things alone: the kind of the state (a check, a statement, a statement's own state or a wait), the state that the base reads at the place or none, the state that the input reads, and the form of the input's right at that place (no right, a right that names no place, a right that leaves the place out, or a right that names it with one state), each judged by its rule (`rightRules`), whose forms are the forms that the test below generates. It reads no base, no words of an input, no reason of its right, and of the place only its kind; a state or a place of no kind, and a form of right that has no rule, is an error, which fails the sweep that meets it. The test below holds that error at each place of each base's answers, under each right and beside each case of the base there: an answer whose input reads, at a place, a value that is no state of the place's kind (a state of another kind, the empty string or a word) fails it unless the judgment refuses the answer, and a base that reads one fails it where it reads the base. The judgment of the reader's answer to an input (`judgeAnswer`) applies it at each place of the answer, and each sweep (`sweepAgainst`) calls that once for each input that the reader reads, with the reader's replies for the base and for the input as its process wrote them, each with the key of the line of the reader's input that it answers (the sha256 of the bytes that the sweep wrote to the process), whether the input has a right, and the places that its right names; the judgment reads the replies' states itself and gives back the keys of both replies, by which the sweep counts the input as read, and the base's digest holds the key of the base's reply and, for each input, the keys of the two replies that the judgment read, so a sweep that hands the judgment, as the base's reply or as the input's, the reader's reply to another line than the one that it stands for (the input's in place of the base's, the base's in place of the input's, or another input's) fails by the digest; it reads no words of a right, and the sweep decides no answer of the reader apart from it. A test generates each case of the judgment's domain from the code's own lists: each kind's states as the reader's code declares them (the constants of the states of a check, of a statement and of a wait, read from the files as the build of the reader's binary reads them, through the overlay that the build reads, which `ENVOY_TEST_GO_OVERLAY`, the build's own flags or `GOFLAGS` gives it; `cmdtest` reads that overlay in one function, which the build and its reading of a file both use) and each form of right that the judgment has a rule for; the value that the input reads and the value that a right names a place with each range over each state of each kind, the empty string and a word that is no state, 2,210 cases; and it compares the judgment with a definition written apart from it from the approved words (R7 to R10, R29 and R48), which a test holds to rows quoted from the approved text. It fails on a case that the definition does not cover, a case that the judgment refuses, and a case where the two disagree, and on a value that is no state of the kind, at the input or at the right, unless the judgment refuses it and the definition covers nothing, so a state, a kind or a form of right that the code gains without a word of the definition fails by name. It also reads each base of the sweeps through the reader and decodes the states of each reply itself, apart from the decoder that the judgment reads replies with, so a base whose reply that decoder reads otherwise (a place dropped or changed) fails by the base's name, and the places that the reader wrote stay in the test's domain; it fails a place or a state of no kind, and hands `judgeAnswer` answers of each base, as replies of the reader's form, whose arguments it ranges over by their types, absence included: no right or a right, whose places are no map or a map; and at each place, the base's state, none or each state of the kind, the input's, none or each of those values, and the value that a map names the place with, or none. Each place takes each of its cases beside the other places as the base reads them, and its states beside the other places taken out of the input's answer or left out of the right, so each base has answers that lack places or hold none, and rights that name places and none of the answer's, or that name none; and answers move each place at once. It holds what `judgeAnswer` reports of each to the definition applied place by place, and to a refusal where the definition covers no reading, so a judgment of an answer that reads the answer by its shape, passes over a place whose input reads a value that is no state of its kind, or reads another right at a place than the input's, fails by the case. A field that a right at a place gains, or an argument of `judgeAnswer` or a type of one that the test does not range over, fails it by name, and so does a reply that gives no states (the reader's refusal, or a line of no form of the reader's), at the base or at the input, unless the judgment refuses it. What it does not prove: that the definition says what the approved words mean beyond its quoted rows, since the definition and the judgment are one reading of those words written twice; and that each sweep hands `judgeAnswer` the input's right and reports what it says, which is the sweep's one call of it (`sweepAgainst`) and its use of the result. Two known positives show that at their bases: at the base wait-cycle, its failing run written as a pass, which moves a check, two statements, an own state and a wait toward true, with no right; and at silent-leg, a leg of a job that ended with no result taken out, which moves a check, statements, an own state and a wait at two subjects, with a right that leaves out each place that it moves at the first subject and names each that it moves at the other with a state that is neither the base's nor the input's. A sweep that skips the judgment for them or counts one as read, or hands the judgment the base's states for the reader's answer, fails by both names; one that hands it a right wider than the input's at the places that the second moves, such as a right that names no place, fails by the second; and one that hands it no right, or a right narrower than the input's, fails by the inputs that move a state toward true by their right. A sweep that handed the judgment another right only at other bases, at other places or for other inputs would not fail, and neither would one that hands it a reply that its own code wrote or whose text or key it set, or the result of a second call of the judgment for an input, or that counts an input by a key that the judgment did not give back; each shows only in the sweep's code. The sweep judges each by the same code as each input and fails by name unless it reports each with exactly the states that it is built to move, and no count or digest holds them. The counts and digests are those that the sweeps gave when the table was written, so a change that adds, takes out or moves an input, writes one with other bytes, or gives one another right, writes the table again. So code that gives an input a right, or widens the places that a right allows, fails by the digest. Many inputs of one place read the same to the reader, and this is by design: they are the sweep's forms of one meaning, such as a member left out, an empty name and a name of one space, each read as nothing. The distinct-input check compares bytes, so it does not compare such forms; a change of them is a change of the sweep's own text, which no writer can make, and the digest fails it, since it holds each input's bytes: with the forms of a string written as an empty name and two spaces, where an empty name and one space are meant, each still read as nothing, the tree sweep fails by its digest at each base. A right that names its places covers only those places. Two rights name no place, and an input that has one is judged by its right alone: a repository path of a tree written as one space, which ends the carry of each result across that tree, and a parent left out of an approved block, which puts its statement at the top of the tree and can leave each statement that was above it met. The places that such an input may move are those that the derivation itself reaches from its change, so a list of them would be a second derivation.

The command tests run the built binary against the fixture scenarios and compare its output with each fixture's `want.txt`. The derivation package is the source of truth for the state rules; this document describes the scenario interface and the invariants at its boundary.
