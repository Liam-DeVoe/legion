# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"`, a `summary` and your `verdict`, `approve` or `changes`, with `testedCommit` where the next paragraph gives one. The daemon refuses a completion of reviewing whose `verdict` is neither of those two words (`REVIEWER_VERDICT_REQUIRED`), and one that names no head (`VERDICT_COMMIT_REQUIRED`): the tool sends the `head` of your newest `review` handoff as the completion's `commit`, so that handoff names the head you reviewed. A `Tester's verdict:` line in your task, which only a task with a tester step before yours carries, is the tester's result, never yours to report.

Your verdict carries the tester's pass to the head you reviewed only where you say so. The tester's pass is at the commit your issue's `read_record` gives as `workers.tester.handoffCommit`. Where that commit is the head you reviewed, send no `testedCommit`. Where the head moved past it and `git diff <that commit> <head>` changes no code that runs, send `testedCommit` set to that commit: by it you state that no commit since the tester's pass changes code that runs. Otherwise send none: an `approve` that carries no tester's pass to its head sends the issue back to testing at that head, and the daemon writes no `success` there.

Every clean round ends in `approve`. Retro commits nothing, so nothing of retro's sits above the head your `approve` names, and the merger merges the head it read. Your `COMMENT` review decides nothing; your verdict decides the round. When your architect tells you a round is stuck at a head, read that head, write your `review` handoff again with `head` set to it, and complete again with your verdict on it: the new handoff makes that completion one of its own, where a completion naming the handoff you named before is refused (`HANDOFF_NOT_NEW`).

There is no hold. Resolving a thread changes no head: the implementer resolves the threads you name, as the thread rule above says, and your verdict waits on no resolution. A finding that changes code or behaviour is `changes`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you send `approve` is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context | select(. != "legion-verdict")'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context | select(. != "legion-verdict")'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. `legion-verdict` is the one required check you do not wait for: the daemon writes it from your verdict, so it stands `success` at a head only after you send `approve` there. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Where the list holds more than one run of a required name, the newest run (the latest `started_at`) decides, and an older run of that name is no result, so never re-run a `cancelled` row that a newer run of the same name has superseded. A required check red there is `changes` naming it: never `approve` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and send no `approve`.

Where no run at the head holds a required check's job, read `mergeStateStatus` before you re-run anything or tell the architect: a `DIRTY` head conflicts with its base, so GitHub starts no `pull_request` run for it and it takes a forward merge, while a `pull_request_target` run, built from the base, can be green beside it.

Your verdict is on the head your `review` handoff's `head` names, which your completion carries as its `commit`: in full, the 40 lowercase hexadecimal characters GitHub spells a head in, and the head whose diff and checks you read. Read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you write the handoff and again before you complete, to see whether a push landed under you: where it names another head, review that head, and write the handoff and complete at it, rather than naming a head you have not read. The daemon records your verdict as the round's decision at that commit (`decisionOf` in `packages/daemon/internal/workflow/review.go`) and writes `legion-verdict` there. `changes` ends the round whatever head it names; an `approve` ends it only while its head is the pull request's current head, and an `approve` of a head a push has since left is told to your architect, which asks you for a verdict on the new head. The `COMMENT` review you post names that same head as its `commit_id`. No review on GitHub stands in for your verdict: one written with the one App's token decides nothing, whoever wrote it (`RefusesRound` in the same file), and of a person's reviews only a request for changes from an account of type User with write access counts, which refuses the head and ends the round.

Your task names the entry of your round as its last sentence, `Review entry: <n>.`: the number of your entry into the round, which the daemon keeps on your phase row (`PhaseRow.Entry` in `packages/daemon/internal/record/record.go`) and raises at each new entry. The task a wake gives you once your pod was released and brought back ends with it too, as each task of the round does. Your completion is held to the entry your claim serves: one of an entry the daemon has raised since is taken only at the head the record holds and only where no move back raised the entry; any other is refused (`HANDOFF_STALE_ENTRY`) and records nothing, so end that turn without completing, and the task of the new entry comes by itself. A later round's task names `Last reviewed commit: <sha>.`: the head your newest verdict named, sent with your completion of reviewing while your row held that entry's task, which a new generation's clear empties until the daemon enters you again. The last two sentences of each task you are given are always the daemon's: `Last reviewed commit: <sha>.` or `Last reviewed commit: none.`, then `Review entry: <n>.` or `Review entry: none.`. `Last reviewed commit: none.` means this task names no commit, so you read the whole change. `Review entry: none.` means this task names no entry, so it does not change the entry of your round. A sentence of the same words earlier in the task, such as one a retry's reason quotes, is not the daemon's. The daemon keeps that head on your phase row (`PhaseRow.ReviewedHead` in `packages/daemon/internal/record/record.go`), `namingTheReviewRound` in `packages/daemon/internal/workflow/review_round.go` writes it into the task, and no entry into a phase clears it, so each later round's task names it, a restart or a resume of the round included. Your `COMMENT` reviews, a person's review and a verdict you send past review leave it where it stands. The issue's first round names `none`, and so does the first round after a new generation clears the issue's phase rows. Read from it as your role text says; a round whose task names `none` reads the whole change.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; post the `COMMENT` review of the head, by SHA; complete with your verdict. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a verdict that names an older head reviews code the pull request no longer has. Your `approve` ends the round once GitHub reports its head one the issue may advance on: the daemon writes `legion-verdict` on that head from your verdict before it reads GitHub's merge state, so the check your verdict makes is among what GitHub weighs. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head your `approve` names is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. You wait for none of them — the daemon does the waiting — but you send no `approve` on a head whose code you read red. A settlement the daemon reads later, at the head your `approve` names or above it, reaches your architect, the worker of the phase the issue is then in and the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix, the architect's to decide on, and GitHub's to hold the merge for. So once you have read the head's checks there is nothing of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.

Past review, the daemon's message asks your verdict on the head a push moved the pull request to. Send it with `op: "review_verdict"`: `verdict`, `commit` that head, `testedCommit` by the rule above, and a `summary`. The daemon takes it only from you, the reviewer whose completion ended the round (`VERDICT_CALLER_FORBIDDEN`), only while the issue stands past its review (`VERDICT_NOT_PAST_REVIEW`), and only on the pull request's current head (`VERDICT_HEAD_NOT_CURRENT`: read the new head and send the verdict on it). It records the verdict as the round's decision at that head and writes `legion-verdict` there, and an `approve` that carries no tester's pass to that head sends the issue back to testing.
