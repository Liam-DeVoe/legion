The schema every other package reads and writes through: ordered migrations applied in one transaction each at boot, the pool, and the session and people rows — which is why it imports `auth`. `internal/pgmigrate` holds the runner's rules, which the secrets broker's runner shares: the whole migration set is refused before anything applies when two files share a version or a file is misnamed or unreadable, and every migration's lock waits are bounded at five seconds. `internal/pgmigrate` reads migration and census SQL as Postgres 18's lexer does.

The schema also announces the changes the background loops wake on: `embeddings_enqueue` notifies `dispatch_embeddings` when it writes a row (0151), a row trigger on `refs` notifies `dispatch_excerpts_owed` for each document mention left owed an excerpt (0153), `delivery_settings_changed` notifies `dispatch_delivery_settings` for a settings change other than freshness (0156), a row trigger on `document_edit_notices` notifies `dispatch_edit_notices` for each notice given a due time (0157), and every event commit notifies `dispatch_events` (0107). The loops' own state is three additions: `reference_excerpt_backoff` (0152), each failing document's version, failures in a row and next attempt; `suggestion_outcome_cursor` (0154), the one row holding the highest event id the outcome sweep has judged by; and `write_suggestions.swept` (0155), whether a pass has judged a suggestion against all its events, with the partial indexes `write_suggestions_unswept` and `write_suggestions_pending_artifact`. The pool's listener pool dials the held LISTEN connections: the delivery hub's and the event stream relay's, the process's one shared listener, which carries the background loops' wakes and the document rooms' room sync, and the document rooms' NOTIFY sender.

The store also holds what the related-item check reads and writes: each project's term statistics (`search_term_stats`, `search_term_totals`, kept up to date under the `search-term-stats` lease), one `related_checks` row per check, and the trigger that embeds an issue as its title and spec (migrations 0139 and 0140). A pass of that refresh applies what changed rather than counting every item again: triggers on `asks`, `comments`, `issues`, `messages` and `document_search` queue each item whose search text a write changed, with the vector it held before (`search_term_queue`, migrations `20261101182508_search_term_queue` and `20261101182522_search_term_queue_triggers`), and a pass drops exactly the queued rows its own snapshot sees, which it writes beside the counts (`search_term_totals.snapshot`, migration `20261101182515_search_term_totals_snapshot`) so that a later pass can tell its own work from another writer's. It holds the items each check offered too, one `write_suggestions` row per item, and `write_suggestions.role` admits three values since migration `20261111212235_write_suggestions_other_project`: `related`, `decision`, and `other_project`, the role of an answered question of another project. That migration drops the narrower check constraint and adds the wider one in one statement, so no moment passes with the column unchecked, and it rewrites no row. No release after it writes a `decision` row, and the rows written under that role before it stay, because each is the record of what its own check offered. The lease pool has one connection per leased loop and per caller of a delivery intake's hold, twenty-three since the records job of the words people ask about (lease `word-records`) and the reviewer's sweep of held texts (lease `reviewer-sweep`) took one each, and the count is not kept by hand: each of those callers reserves its connection by name before the server starts any of its loops, whether or not this configuration runs its loop, and a server whose reservations are not exactly the pool's size refuses to serve, naming them (`store.LeaseCallers`). The check sees only callers that reserve a name: a goroutine added inside a caller that has reserved already, or one reservation passed to a second consumer, takes a connection nothing counted, and the count still matches.

The store holds what the work on agents' texts records. `writing_check_events` (migrations `20261113085841_writing_check_events` and `20261113165433_writing_check_events_reader`) is one row for each decision of the writing check and the reviewer and for each Rewrite a person asks for, with its outcome, route, writer, reader and project, and a daily sweep deletes the rows past 90 days. `held_texts` (`20261115084745_held_texts`) keeps a text the reviewer holds, under the id reserved for it, and nothing else of the text is written until it posts; `asks.held_until` and `doc_ask_block_authors.person_typed` (`20261115104117_held_decision_blocks`) keep a held decision block out of people's Inboxes and counts and mark a block a person typed. `word_questions` and its one-row cursor `word_records_cursor` (`20261115061524_word_questions`) hold the records job's verdict on each text a person wrote and each Define use, and hold no text. `ask_rewrites` and `definitions` (`20261115122725_rewrites_and_definitions`) hold the latest Rewrite of each ask, one at a time, and each person's own definitions.

It holds the near-copy gate's record too: one `near_copy_checks` row for each answer the gate gives an issue create (`20261115182525_near_copy_checks`), with the outcome, the reason a check was not made, the candidates it read with their scores, the two bars and the build's commit, and the spec of a refused create alone, which no issue holds. A refusal's row is written before its `409`, a create's row after its commit or, for a refusal whose row could not be confirmed, in the create's own transaction, where it replaces a refused row under the same id; table checks keep a refused row free of an issue and every other row free of a spec. An issue the reviewer holds writes its row when it posts, not at its hold.
