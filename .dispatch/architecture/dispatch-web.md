The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

The search palette is also the command bar (`features/search`). Where `GET /api/v1/going/capability` says that an answering model is configured, `useGoingAnswer` asks a question on the pause the meaning search waits for (`MEANING_PAUSE_MS`), never on a keystroke. It sends the words, the filter chip's project and the context chip to `POST /api/v1/going/requests`. It reads the run's stream through `api/event-stream.ts` and not through `EventSource`, so the request carries the page's own headers and can be aborted. The bar holds one run at most, and the next keystroke and closing the bar each cancel it (`POST /api/v1/going/requests/{id}/cancel`). What the panel drew of a run the person typed past stays as it stood at the keystroke, marked as the answer to the earlier words, until the answer to the new words has text of its own, finds none or fails; emptying the box or closing the bar clears it, and the bar's operations read only the answer to the words in the box. `AnswerPanel.tsx` draws the answer beside the hits: the `text` frames as escaped plain text, the `item` frames as the answer's only links, and one line each for a cut, a change the server made, no answer, an answer that rests on no source, the roster's age or a stored roster, and a failure. What this Dispatch cannot do - each missing part of the capability read (`capabilityGaps`), and a search that ran on words alone - is said once in the bar's foot (`CapabilityNote.tsx`) from the moment the bar opens, never under an answer, and not at all where every part is configured and meaning search runs. `blocks/AnswerBlock.tsx` draws the `block` frame, with one component for each of the seven kinds, from the frame's rows alone. `ChartBlock.tsx` loads `echarts` by one dynamic `import()`, as the delivery timeline does, so the chart's chunk arrives with the first chart an answer draws and the shell's entry chunk holds none of it; the chart's rows are also written as a table under the canvas. The page keeps the last answered run outside the dialog, and the bar opening again with an empty box draws that run again from its stream's first frame while Dispatch keeps it. The page stores nothing of a chart.

The bar's operations (`OperationRows.tsx`, `going-turns.ts`) come from the `decision` and `proposal` frames. Where the decision acts, the operation is one row above the hits with a Run button, and it runs on submit: `Mod+Enter` anywhere in the bar, the Run button, or Enter on that row. The highlight never moves to that row by itself, so Enter keeps its one meaning, opening the highlighted row. Below the action threshold the two best actions are rows of their own, and neither runs until the person picks it. A submit before the proposal arrives says the row is preparing and runs when the proposal lands. An invocation that misses one argument asks for it first: a text, a number, a choice, or an item of the hits. A new issue and a send to the issue's agent stay the bar's two offers, which always ask, and they write through the run when the decision chose them. Each invocation is one write of the page's write store (`Writes.run`) to `POST /api/v1/going/runs/{id}/writes`, on the run's own line, so the writes go out one after another, and each write shows its own line: the item, the field, the value before and the value now, or the refusal. Each write and each undo that lands has the bar read its hits again (`goingWrite`, a write kind of its own), so a hit shows the status the turn left and never contradicts the turn's lines. The bar sends an invocation once (`runGoingWrite`): while its write is queued, out or landed, a further submit sends nothing and answers that write's own line, and only a refused write is sent again, by a further submit. Where the setting asks first, the confirm step lists exactly the writes its Confirm sends: every one of the action not still sending or done, a refused one included. A turn's Undo stops each write that still waits its turn before it is sent, waits for the writes that are out, and then sends `POST /api/v1/going/runs/{id}/undo`. `Mod+Z` (`app.tsx`, a global binding that does not run in an editable field, so an editor's own undo is untouched) undoes the person's newest turn from any page: the turn this page is still writing, or else the newest undoable run of `GET /api/v1/me/going-runs?undoable=true&limit=1`, so the key works after a reload. `GoingUndoNotice.tsx` says in the shell's corner what that undo did. Settings has a **Command bar** section (`features/settings/CommandBarSection.tsx`) that reads and writes the person's `confirm_writes` (`GET` and `PUT /api/v1/me/going/settings`). With it on, the bar shows each write it would make and sends it `confirmed` only after the person confirms. A write Dispatch refused `409 GOING_CONFIRMATION_REQUIRED` was sent at once on a copy of that setting the page read before the person turned it on, in Settings or another tab. That refusal says the setting is on, so the page's copy says so at once and is read again behind it (`goingWrite`'s `undone`), and the write's line counts as not yet run (`awaitsConfirmation`): its Run row and Run button stay, with the bar's run hint, and the next submit - the button, the row or `Mod+Enter` - asks first, as the refusal's own words tell the person, with no write sent at once in between.

The browser suite has a models lane (`bun run e2e:models`, `DISPATCH_E2E_MODELS=fake`). It starts a fake writing model and a fake decision model over https on loopback, with a certificate the harness makes (`e2e/harness-models.ts`, `e2e/fake-chat-model.ts`, `e2e/fake-decision-model.ts`), and configures the server with the model that `packages/envoy/going/decision_models.json` marks chosen. Its specs read every threshold from that record. The default stack configures no model, and `e2e/going-unconfigured.e2e.ts` is its row; that row skips in the models lane unless `DISPATCH_E2E_CONTROL=unconfigured-in-models-lane` runs it there as its check's negative control, which fails.

Its path `packages/dispatch` also holds `e2e/read-token-live.ts`, the live proof that drives a read-only token from `packages/envoy/scripts/dev-broker.sh` against a `bun run dispatch:local` Dispatch and expects `200` on the architecture route and `403 READ_ONLY_TOKEN` on a comment and an issue read.
