The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v2/settings/credential-broker`, which `GET /api/v1/credentials/capabilities` answers for older builds), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

Its path `packages/dispatch` also holds `e2e/read-token-live.ts`, the live proof that drives a read-only token from `packages/envoy/scripts/dev-broker.sh` against a `bun run dispatch:local` Dispatch and expects `200` on the architecture route and `403 READ_ONLY_TOKEN` on a comment and an issue read.

From the first `legion-envoy` release that carries pull request #4274 the application calls Dispatch's `/api/v2` alone, through the paths and types `@legion/contracts/dispatch-api-v2` generates from the `/api/v2` OpenAPI document (`web/src/api/paths.ts`, `api/client.ts`), so a path the document does not hold fails `tsc`. It reads each list it shows whole page by page at the route's default `limit` until it holds `total` rows or a page comes back short (`readWholeList`), keys every write, `PUT` and `DELETE` included, and reads both `/api/v2`'s `NO_ROUTE` and an older server's `NOT_FOUND` "no route" as a route a rolling release has not reached yet (`isNoRoute`). The one `/api/v1` call left replays a write an older build saved (`features/writes/write-storage.ts`) to the path it was first sent to under its own key; a replay answered `410`, once the deployment has ended `/api/v1`, is dropped and the page says the write was not saved. Its browser suite (`e2e/`) and the stubbed layer's recordings call and hold `/api/v2` alone too.
