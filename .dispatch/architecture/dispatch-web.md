The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

The search palette is also the command bar (`features/search`). Where `GET /api/v1/going/capability` says that an answering model is configured, `useGoingAnswer` asks a question on the pause the meaning search waits for (`MEANING_PAUSE_MS`), never on a keystroke. It sends the words, the filter chip's project and the context chip to `POST /api/v1/going/requests`. It reads the run's stream through `api/event-stream.ts` and not through `EventSource`, so the request carries the page's own headers and can be aborted. The bar holds one run at most, and the next keystroke and closing the bar each cancel it (`POST /api/v1/going/requests/{id}/cancel`). What the panel drew of a run the person typed past stays as it stood at the keystroke, from the very render the words change in, marked as the answer to the earlier words - and, where that run was still writing it, as one that stopped before it finished - until the answer to the new words has text of its own, finds none or fails; emptying the box or closing the bar clears it, and the bar's operations read only the answer to the words in the box. `AnswerPanel.tsx` draws the answer beside the hits: the `text` frames as escaped plain text, the `item` frames as the answer's only links, and one line each for a cut, a change the server made, no answer, an answer that rests on no source, the roster's age or a stored roster, and a failure. What this Dispatch cannot do - each missing part of the capability read (`capabilityGaps`), and a search that ran on words alone - is said once in the bar's foot (`CapabilityNote.tsx`) from the moment the bar opens, never under an answer, and not at all where every part is configured and meaning search runs. `blocks/AnswerBlock.tsx` draws the `block` frame, with one component for each of the seven kinds, from the frame's rows alone. `ChartBlock.tsx` loads `echarts` by one dynamic `import()`, as the delivery timeline does, so the chart's chunk arrives with the first chart an answer draws and the shell's entry chunk holds none of it; the chart's rows are also written as a table under the canvas. The page keeps the last answered run outside the dialog, and the bar opening again with an empty box draws that run again from its stream's first frame while Dispatch keeps it. The page stores nothing of a chart.

The bar's operations (`OperationRows.tsx`, `going-turns.ts`) come from the `decision` and `proposal` frames. Where the decision acts, the operation is one row above the hits with a Run button, and it runs on submit: `Mod+Enter` anywhere in the bar, the Run button, or Enter on that row. The highlight never moves to that row by itself, so Enter keeps its one meaning, opening the highlighted row. Below the action threshold the two best actions are rows of their own, and neither runs until the person picks it. A submit before the proposal arrives says the row is preparing and runs when the proposal lands. An invocation that misses one argument asks for it first: a text, a number, a choice, or an item of the hits. A new issue and a send to the issue's agent stay the bar's two offers, which always ask, and they write through the run when the decision chose them. Each invocation is one write of the page's write store (`Writes.run`) to `POST /api/v1/going/runs/{id}/writes`, on the run's own line, so the writes go out one after another, and each write shows its own line: the item, the field, the value before and the value now, or the refusal. Each write and each undo that lands has the bar read its hits again (`goingWrite`, a write kind of its own), so a hit shows the status the turn left and never contradicts the turn's lines. The bar sends an invocation once (`runGoingWrite`): while its write is queued, out or landed, a further submit sends nothing and answers that write's own line, and only a refused or stopped write is sent again, by a further submit. The Operation row names, the fill step asks the missing arguments of, and where the setting asks first the confirm step lists, exactly the writes that press sends (`unsettledIndexes`): every automatic one of the action not still sending or done (`settlesInvocation`), a refused or stopped one included; a press with none of them left asks nothing and sends nothing. A turn's Undo stops each write that still waits its turn before it is sent, waits for the writes that are out, and then sends `POST /api/v1/going/runs/{id}/undo`. `Mod+Z` (`app.tsx`, a global binding that does not run in an editable field, so an editor's own undo is untouched) undoes the person's newest turn from any page: the turn this page is still writing, or else the newest undoable run of `GET /api/v1/me/going-runs?undoable=true&limit=1`, so the key works after a reload. `GoingUndoNotice.tsx` says in the shell's corner what that undo did. Settings has a **Command bar** section (`features/settings/CommandBarSection.tsx`) that reads and writes the person's `confirm_writes` (`GET` and `PUT /api/v1/me/going/settings`). With it on, the bar shows each write it would make and sends it `confirmed` only after the person confirms. A write Dispatch refused `409 GOING_CONFIRMATION_REQUIRED` was sent at once on a copy of that setting the page read before the person turned it on, in Settings or another tab. That refusal says the setting is on, so the page's copy says so at once and is read again behind it (`goingWrite`'s `undone`), and the write's line counts as not yet run (`awaitsConfirmation`): its Run row and Run button stay, with the bar's run hint, and the next submit - the button, the row or `Mod+Enter` - asks first, as the refusal's own words tell the person, with no write sent at once in between.

The browser suite has a models lane (`bun run e2e:models`, `DISPATCH_E2E_MODELS=fake`). It starts a fake writing model and a fake decision model over https on loopback, with a certificate the harness makes (`e2e/harness-models.ts`, `e2e/fake-chat-model.ts`, `e2e/fake-decision-model.ts`), and configures the server with the model that `packages/envoy/going/decision_models.json` marks chosen. Its specs read every threshold from that record. The default stack configures no model, and `e2e/going-unconfigured.e2e.ts` is its row; that row skips in the models lane unless `DISPATCH_E2E_CONTROL=unconfigured-in-models-lane` runs it there as its check's negative control, which fails.

An upload from the browser names the token of the version it replaces, read when the person chooses the file. `captureUploadBase` (`features/artifacts/ArtifactUpload.tsx`) reads the token of the document the owner already holds under the name being uploaded, through the route that resolves a slug or a filename (`api/client.ts`'s `ownerArtifactText`), and the press sends it as the upload's `precondition`. So the window this guards runs from the choice of the file to the post: a write landing in it is refused `409 PRECONDITION_FAILED` rather than written over, and a change made before the file was chosen is replaced with no refusal, since the upload names what the document said at the choice. Reading the token from the open document instead, and holding it while the person reads, would guard nothing more: the document view is a live room, so the text in front of that person is the current one by construction. The token is read once for the press and every attempt of that press sends it, because Dispatch's idempotency key digests the whole body, the `precondition` field included (`bodyDigest` in the server's `api/request_keys.go`): an attempt that read the token afresh would send other bytes and be answered `422 KEY_REUSED` instead of what the first attempt did. A press after Dispatch has decided one reads the token again, so pressing Upload after a refusal names what the document says now, under a key of its own.

It names no token only where there is none to name: a conversation, which holds files and images and no document; a file whose media type is not `text/markdown`, parsed as the server parses it (`mime.ParseMediaType` in `artifactKind`, so `text/markdown; charset=utf-8` is a document here too); and the two answers that mean the owner holds no document to replace - `404 ARTIFACT_NOT_FOUND`, the first upload under that name, and `409 DOC_SCHEMA`, a tree outside the Proof schema, which renders no markdown and so has no token and which an upload is the only way to repair. Every other failure of that read - the request never reached Dispatch, the session lapsed, a 5xx, `400 ARTIFACT_REFERENCE_AMBIGUOUS` - ends the upload with its own message and posts nothing: the page does not know what it would be replacing, and an upload naming no version replaces it silently. The Plan and Verification tabs' empty states print the `dispatch artifact` line that makes the document and, under it, that a later upload under that name replaces the document and takes `--precondition-json` with the token `dispatch doc-read` prints.

What a refused upload says is the page's own words, not the server's. The server writes its refusals of that token for a caller holding the `dispatch` command, naming the command that reads the token and the argument that sends it; a person uploading here runs no command and pastes no token, so `uploadErrorMessage` answers each in words of its own and passes every other refusal through as the server wrote it. They are three different things to be told: `PRECONDITION_FAILED` is `UPLOAD_BASE_REFUSAL`, the document changed while they were uploading it, so open it and upload again; `PRECONDITION_REQUIRED` is `UPLOAD_BASE_REQUIRED_REFUSAL`, the upload named no version where Dispatch requires one, which from this page means the read found no document and one was created before the post; and a token the page could not read at all is `UPLOAD_BASE_UNREADABLE_REFUSAL`, nothing was uploaded, followed by what Dispatch said of the read. `e2e/artifacts.e2e.ts` proves the guard in a real browser against a real server: it reads the `precondition` field out of the page's own multipart request and compares it with the live token, then holds that request in a route while an agent edits the document, so the token the server reads is one version behind and the row shows the refusal. That reading of the request is the only evidence of its kind here, since every unit test of this path mocks the client the page uploads through and asserts its argument, which is how `ApiClient.uploadArtifact` came to drop the `precondition` from the body it posts without a test noticing.

A composer's draft - typed, refused or stopped - goes where the person takes it, and stays where the host moved away from; neither lets what the person wrote go with no word. A move the reader makes with the composer's own controls - Cancel reply, Escape, and a control the host draws for it and counts in the same press (`ownMoves`, the Agents row's issue picker) - carries the draft's refusal to the new address (`HeldSends.carry`, `features/conversation/held-sends.ts`), where Send and Retry go under a key of their own, and re-points the files pasted into it (`draftHomes` in `useDraftHomes`), so a file that lands afterwards adds its reference at once, naming the owner it went to. A move of the host's - another row, another thread, a Reply on a message, a phone thread's Back - carries nothing: `HeldSends.send` refuses a press whose address is not the refusal's (`sameAddress`), and the composer says where the draft was written for. A typed draft stays as well: a composer its host moves from reply to reply, or takes off the page - the docked composer, a phone thread's, an Agents row's, the margin's compose - keeps what the field holds for the reply it answers, or for none (`AwayDraft` in `features/conversation/unsent-drafts.ts`, under the send name), puts it back in place of a new reply's prefill when it is at that address again, and while it shows another address says the text is kept, whose message it answers and the way back (`keptAwayLine` in `KeptReply`). The reader's own move onto an address that keeps a draft of its own carries nothing, so neither draft is written over. Text typed while the host holds a composer away from a refusal's address is that address's and is kept for it, and the refusal keeps its own draft. Leaving a document leaves the margin's unsent compose open for it (`useMarginSheet`), and the margin holds one open compose per document (`composeForMark` replaces only the compose on its own document, and takes its provisional mark out through that document's bridge), so a compose opened on another document leaves it open too, and the compose and its text are there on return. The margin's compose keeps its draft for the words it was written about (`AwayDraft.anchor`, which `readAway` compares) and the kind it was written as (`AwayDraft.kind`): a newer compose on the same document draws a composer of its own (`MarginSheet` keys it by its compose), and the earlier draft - typed, or handed back by a refusal, whose refusal goes - is never put in its field, while a send the person stopped, which may have been delivered, waits aside whole (`marginComposeKeptKey`). Either waits beside the newer compose, the field and an ask's fields read only and Send refused, naming the quote it was written for, the kind it was written as where the compose is another, and, for a stopped send, that it may have been delivered there and that sending it from here is a new message (`SendMovedError`), until the person presses Use my draft, which puts it in the field with an ask's options and settings (`AwayDraft.ask`) and carries a stopped send into that compose as the reader's own move carries one (`HeldSends.carryInto`), so the same words stay with Retry and Discard draft until it is sent or discarded, or Discard my draft (`offered` in `useKeptDrafts`); neither retypes the compose or its mark. A standing box's draft is its thread's, which a newer message the box moves onto leaves in the field. A stopped send may have been delivered, so its key is never used away from its own address: carried by the reader, it goes on as a new write, and its refusal says the first may already have been delivered (`SendMovedError`). On a phone the thread view's own composer does as the docked one does: its Cancel reply ends that composer and puts its draft, the refusal with it, in the docked composer at the issue's address (`HeldSends.carryInto`, `usePhoneThread`'s `cancelReply`), and while the docked composer holds a draft of its own, which is never written over, the thread composer is put away as it stands, the docked composer says the reply is kept, and that comment's Reply brings it back. A thread card's inline reply has no other composer to go to, so its Cancel reply ends the reply and keeps the draft under its own send name - typed (`unsent-drafts.ts`), refused or stopped (the held send) - and the closed card says the reply is kept and how to go on with it (`keptReply` on `ThreadCard`); its Reply brings the draft back with its refusal, and nothing is sent until the person presses. The phone thread views' Back - the margin sheet's (`closeThread` in `useMarginSheet`) and the Conversation's (`usePhoneThread`'s `leave`) - drops nothing: the card's reply and the thread composer's stay held for their thread, and opening it again brings them back.

A comment's editor keeps what the person wrote the same way when its host takes it off the page - Collapse thread, another thread opened in the margin, a phone thread view's Back - with the comment's body it was written over (`AwayDraft.base`; a refused edit's request carries its own, `SentRequest.edit.base`), and the editor drawn for that comment next puts the edit back only while the comment still holds that body, or reads as the edit would save it (`changedUnder` in `useKeptDrafts`). Over a body another writer has changed since, the field shows the newer body, read only, and the edit waits beside it with words saying the comment changed since the edit was written (`changed`); Save refuses until the person presses Use my edit, which puts the edit back in the field for their own Save, or Discard my edit, so nothing is saved over a version of the comment the person has not seen. A change under an open editor does the same: the field takes the newer body, and what the person wrote waits beside it, kept at once in its refusal or for the comment with the body it was written over, so a host's move meanwhile loses nothing; while a save of the editor's own is out, the field only takes the body. The Conversation keeps each thread's open editor by its root (`editingIn` in `ConversationTab`), as the margin keeps its own (`useMarginSheet`), so a phone thread view drawn afresh opens with it.

Every draft store keeps the person's unsent drafts in the tab's `sessionStorage` (`draft-store.ts`), beside the unconfirmed writes (`write-storage.ts`), so a browser that restores or duplicates a tab restores or copies both with it. A duplicated tab takes the copied writes up again, as the first tab does, which is safe: a `PUT` or a `DELETE` makes the same change again, and Dispatch answers a `POST` or a `PATCH` under its kept key with what the first one did. A draft sent from one of the two tabs stays in the other, where sending it is a second message.

A read-mark's answer is put into the viewer's shared agent-state query over every read of that query still out: such a read was asked before the mark, and its later answer would put back the unread count the mark cleared for that session, so the compact header's and the navigation's badge would read "New reply 1" again. `replaceQueryData` (`api/query-client.ts`) cancels the query's reads and writes in the same synchronous step, as `askSignInAgain` and the board's moves do, and `storeAgentState` (`features/agents/unread.ts`) writes through it. A read it cancels was asked for news of its own - another session's new reply, or the page's first load of every session - so when it cancelled one, it asks the query again once the write is in (exact, active queries only), and that read, asked after the mark, brings that news beside the mark's answer. The web app's other writes of a server's answer into its cache are counted, each with its verdict, at dispatch://INFRA-1503/artifact/cache-write-class-md.

Its path `packages/dispatch` also holds `e2e/read-token-live.ts`, the live proof that drives a read-only token from `packages/envoy/scripts/dev-broker.sh` against a `bun run dispatch:local` Dispatch and expects `200` on the architecture route and `403 READ_ONLY_TOKEN` on a comment and an issue read.
