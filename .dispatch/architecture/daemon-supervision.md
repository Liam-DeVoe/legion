Stage 2 on `main` provides the fenced role-claim state machine and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that ends the largest process that is neither Legion's own nor an agent's own when the pod nears its memory limit, and reports the kill on the role's launcher connection (`launcher_memory_kill`), from which the daemon tells that role why on its role topic.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of the role's own private volume. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).

The work hold's stop is a suspension source of its own, `hold` (`supervise.SuspendedByHold`, `internal/supervise/workhold.go`). Like any held suspension, it waits for the agent's turn, and it cuts a turn that still runs at the deadline the outbox stores, 2 minutes after the close message reached the claim (`RequestSuspend.Deadline`, `RequestSuspend.TurnAfter`). The claim keeps its session, its phase and its pending task. No rule starts it: the fence answers every request that could start a turn of the claim (`ruleDoor`) with a wait, `ErrHeldByWorkHold`. Only the operator's own resume or retry (`ownerDoor`) or the hold's end (`Machine.EndHold`) starts it. `EndHold` drops a stop that is not made yet, and starts a claim the hold stopped with one task, the opening's sentences in front of its work. The hold's stop does not cut a start in flight short: it waits for the start's decision. An operator's suspension and the daemon's own take a held claim over, and the hold takes over a released claim and a pause's stop (`suspensionRank`). The idle rule keeps the pod of a claim the hold stopped (`workflow.IdleHoldUnownedWorkHeld`).

The stop and the opening use one row: the tree's `work_holds` row. A decision that can make the hold's stop reads this row for share, and releases the lock at once (`Store.LockWorkHold`, `readHoldForStop`). Such a decision is a decision of a claim whose hold stop is held, or the decision of the hold's stop itself. A tool step and a model's answer read nothing, because their rows only record what the agent did. The opening takes the same row for update before it reads the tree's claims, and deletes the row in the same transaction (`workflow`'s `tellAndEndWorkHold`). In that transaction, the opening also writes the hold and what ended the hold to `work_hold_openings` (`record.Store.OpenWorkHold`). The read does not read that table. A read that starts while the opening holds the row waits for the opening's commit. If the opening commits first, the decision reads no row and makes no stop: it drops a held stop, and the hold's stop asked now answers `ErrWorkHoldEnded`, so the outbox finishes the stop's row. The wait for the read ends at the claim-write deadline. If the read fails, a held stop stays held, and the stop's outbox row asks again.

No decision holds the row after its read. The opening waits for the row under the lock that every fact takes. A decision that held the row across a call of the runtime, such as a process stop, stopped every fact of the daemon for as long as the call ran, or until the database ended the idle transaction after 30 seconds. So the opening can commit after a decision read the row and before that decision writes the stop. One case remains: a stop decided in the instant before an opening commits is made, and the claim is started at once with the opening's task, as the next paragraph says.

Because the opening can commit before a stop is written, the opening can read a claim before its stop is written, and start nothing of it. So after each write of the hold's stop, the machine reads the row again for share, in a new transaction, and ends that transaction at once (`holdReadAfterStop`). This read waits for an opening that holds the row. If the row stands, a later opening reads the stopped claim and starts it. If the row is gone, the machine tells the daemon (`Deps.WorkHoldEndedUnderStop`). The daemon then applies `intake.WorkHoldOpened` at once. This fact starts each claim that the hold stopped and that no opening start covers, so no claim starts twice.

If the read fails, the decision returns the error, and the stop's outbox row asks again. If the next attempt meets the open gate, the row applies the same fact (`holdStopUnmade`). If the next attempt posts the stop again and the decision reads no row, the machine tells the daemon, as above, and the row finishes. If the write of the stop fails, the machine keeps that write owed, and no read follows. Each decision first makes an owed claim write, and `DropHoldStop` and `EndHold` do this too. If the write fails again, the store does not hold the stop, so the machine does not tell the daemon. Then `DropHoldStop` and `EndHold` change nothing and return an error. The stop asked again returns an error, not `ErrWorkHoldEnded`. In each case, the outbox row asks again.

Each start of a claim that the hold stopped gives the claim one task, and one function builds the start of that task (`workflow`'s `heldClaimOpening`). The opening, the read after the stop, the stop asked again and the boot all use it. The opening builds the task from the row that it moves into the tree's record of its last opening. Each later start reads that record (`record.Store.TreeWorkHold`). The task names the version that closed the gate, says that the work hold stopped the turn, and carries what ended the hold: today's open message, or the boot's sentence when the deployment no longer holds the tree's work. If the tree's record shows a hold that stands, the hold stands again, and the start does not occur. If the daemon keeps no record of the hold, or the record is of an older generation of the tree, the task says that the hold has ended and that the daemon keeps no record of the version that closed the gate. This occurs after a new generation of the tree. The task never says that the deployment no longer holds the work, unless the boot ended the hold for that reason.
