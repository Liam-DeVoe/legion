Stage 2 on `main` provides the fenced role-claim state machine and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that ends the largest process that is neither Legion's own nor an agent's own when the pod nears its memory limit, and reports the kill on the role's launcher connection (`launcher_memory_kill`), from which the daemon tells that role why on its role topic.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of the role's own private volume. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).

The work hold's stop is a suspension source of its own, `hold` (`supervise.SuspendedByHold`, `internal/supervise/workhold.go`). Like any held suspension, it waits for the agent's turn, and it cuts a turn that still runs at the deadline the outbox stores, 2 minutes after the close message reached the claim (`RequestSuspend.Deadline`, `RequestSuspend.TurnAfter`). The claim keeps its session, its phase and its pending task. No rule starts it: the fence answers every request that could start a turn of the claim (`ruleDoor`) with a wait, `ErrHeldByWorkHold`. Only the operator's own resume or retry (`ownerDoor`) or the hold's end (`Machine.EndHold`) starts it. `EndHold` drops a stop that is not made yet, and starts a claim the hold stopped with one task, the opening's sentences in front of its work. The stop and the opening use one lock: the tree's `work_holds` row. A decision that can make the hold's stop takes this row for share, and holds it until the decision ends (`Store.LockWorkHold`, `lockHoldStop`). Such a decision is a decision of a claim whose hold stop is held, or the decision of the hold's stop itself. A tool step and a model's answer take no lock, because their rows only record what the agent did. The opening takes the same row for update before it reads the tree's claims, and deletes the row in the same transaction (`workflow`'s `tellAndEndWorkHold`). If the stop commits first, the opening reads the claim stopped and starts it. If the opening commits first, the decision reads no row and makes no stop: it drops a held stop, and the hold's stop asked now answers `ErrWorkHoldEnded`, so the outbox finishes the stop's row. The wait for the lock ends at the claim-write deadline. If the lock is not granted, a held stop stays held, and the stop's outbox row asks again. Two calls release the lock before the decision ends. Each of these calls can wait for the lock that every fact takes, and the opening holds that lock while it waits for the row. A durable state's report releases the lock before the daemon hears the state (`Machine.report`). The report of a ready or a failure applies a fact. The launch check releases the lock before the store checks the tree's epoch (`Machine.checkLaunch`). The decision of the hold's stop can make a report before its stop. This occurs when an earlier write of the decision lands the write of a failed decision, with the reports of that decision. Then the decision makes no stop, and it answers `ErrWorkHoldLockEnded`, which is a wait (`holdStopUnlocked`). The outbox asks the stop's row again, and the next decision takes the lock again. A held stop can be made without the lock in three cases. The lock was not granted. A report or the launch check released the lock. The database ended the lock. In each case, the stop's row starts the claim when it meets the open gate (`holdStopUnmade`, `intake.WorkHoldOpened`). The hold's stop does not cut a start in flight short: it waits for the start's decision. An operator's suspension and the daemon's own take a held claim over, and the hold takes over a released claim and a pause's stop (`suspensionRank`). The idle rule keeps the pod of a claim the hold stopped (`workflow.IdleHoldUnownedWorkHeld`).
