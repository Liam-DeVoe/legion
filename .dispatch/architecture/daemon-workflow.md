Planned: the issue-cap admission line, durable Dispatch and GitHub event intake, classification, the transition table, status and notice effects, and the Go Dispatch client — `internal/admit`, `internal/intake`, `internal/workflow`, `internal/classify`, `internal/dispatch`, `internal/notify`, `internal/phase`. LEGION-219 (Stage 3) carries them; none exists on `main` yet, so this component has no paths. The planned workflow advances phases from facts the coordinator observes; agents do not choose the next phase.

Admission and the workflow read the deployment's repository equivalence (`repository_renames`, `config.Config.RepositoryRenames`, a `ghrepo.Renames`) wherever they compare a repository's name, so a transfer that renames a repository leaves the trees already recorded under the old name running: in intake, `ConsumerSpec.Renames` carries the pair into the consumer's `recordedPullRequest` read; in `workflow`, one `Engine.sameRepository` stands where `strings.EqualFold` stood, at `issueForBranch`, `ownPullRequest`, the opened handler's redelivery test, `check.go`'s comparison of a recorded check, and `NoteRepositoryKept`, which therefore says nothing when Dispatch re-points an issue at the repository the one it is recorded on moved to. No deploy run is matched any more: the production check a merge opens is woken only by the `wake_at` its own agent — the role the project's `production_check` names — gave on a `pending` report, by the retry of a look nobody reported, or by the check's own bound, so `projects.<KEY>.deploys` is read for nothing and only warned about. The reads keyed on the `pull_requests` table's `repo` column — the engine's `pullRequest` and `pullRequestByBranch`, `internal/daemon`'s `reviewedRepository` and intake's `recordedPullRequest` — ask under each name `Renames.Lookups` gives, the fact's own first and the pair's other name only when the first finds nothing, which is what lets a pull request already open at the transfer go on taking its CI, its review and its merge. The equivalence writes no record but for one pass of this release, `internal/daemon`'s rename pass (`record.RenameIssueRepository`), which writes each pair's `to` over its `from` on the stored rows of each issue with no live pod, at boot and when the issue's pod ends; until it writes a record, the record keeps the repository it was written under, so the pair must stay configured until no row names the old repository. It serves no repository of its own either — a name is served when GitHub answers that both role Apps are installed on it, and until GitHub has answered for a pair's names its `to` counts as served and its `from` does not — so a pair may be configured before the transfer and simply answers nothing until the events arrive under the new name.

A new version of an approved document of a gated step closes the tree's standing gate (`classify.StandingGate`), and the deployment's `gates.hold` (`Config.Hold`) says what the closed gate holds. Under `merge`, the default, the merger's start and the first phase of each issue that has not started wait, and `tellGateMoved` tells each phase worker of the tree and the root's architect of the move. Under both holds, the close message to a merger whose idle pod the daemon released is marked to wake it (`record.RoleMessage.Wake`), so the merger can take its pull request out of GitHub's merge queue. Under `merge`, the close also gives that mark to the message to a merger whose claim is live, or whose start a lane runs now (`mergersToWake`): the outbox reads the gate once before a start acts, so such a merger can launch with its task after the close, and the message waits for the merger's session. A message to a merger with no claim yet, or with a claim that runs nothing and is not released (suspended by the daemon or an operator, failed or retired), waits only while a lane runs a start of the merger or the record holds a claim of it that is not gone, and while its issue can be woken, and otherwise finishes with no stop (`internal/daemon`'s `closeWaitsForAMerger`). A merger whose start is only queued gets no mark: that start waits at the fence through the hold, and a message that waited for it would keep the issue's pod from its idle release. Under both holds, every message of the close, the architect's among them, is marked as a close message (`record.RoleMessage.Close`). Such a message reads the standing gate at the head of each attempt, and finishes unpublished, with no stop, when the gate no longer stands closed, or when its stop names an older version than the tree's hold that stands (`internal/daemon`'s `closeOutrun`). Under `work`, the move is the work hold's close or its opening (`internal/workflow/work_hold.go`). The close writes the tree's `work_holds` row (`record.WorkHold`) and tells every live architect and phase worker of the tree, and each phase worker's message carries its stop (`record.RoleMessage.Stop`, a `record.HoldStop`, from which the outbox builds the suspend once the message ends). It records the hold at once on a released worker that is not a merger. It also records the hold at once on a phase worker that is neither live nor released while a start of it is under way (`StartUnderWay`). That start read the gate open before the close, and the stop, which the outbox runs after the start, stops the launching claim at its ready, before the claim takes a task. A wake that passed the fence can launch a released worker after the close in the same way. Both stops that the close records at once store a deadline 2 minutes after the close, so where a daemon restart or a failed attempt of the stop lets the ready come first, the stop cuts the claim's turn at that deadline. The opening tells every live holder the open message, deletes the row, and starts each claim the hold stopped, and no other, with one task that begins with the opening's sentences (`openHeldClaims`). It writes no start where a queued start of the opening stands (`OpeningStartStands`). In the same transaction, it keeps the hold and the open message as the record of the tree's last opening (`work_hold_openings`, `record.Store.OpenWorkHold`). A claim that the hold stopped after the opening read the tree's claims is started later with the same task, built from that record (`heldClaimOpening`). A start that the outbox runs against a claim that the hold holds builds its opening's sentences from that record when it runs (`HeldClaimOpening`), so a start queued before a later close and opening gives the later words. Where the claim kept an earlier opening's task, the new task carries the newest sentences once, in front of that task's work (`supervise.Delivery.Work`). The boot reconciles each running tree with its row (`workHoldBooted`). The standing gate (`record.TreeGate.Standing`), read under `work` alone (`holdIsWork`), is the one predicate that the close, the opening and the boot read, and `internal/daemon`'s start fence (`startWaitsForTheHold`) reads the same standing gate. The state's `why: held` reads the tree's `work_holds` row.

Each path that tells a root architect of an approval (the `design-approved` and `carried-gate-opened` notices, the role message that the gate opened, a resume or start task, the catch-up, and a decision kept for a parked root) reaches the architect after the transaction that writes the gate row commits, so pi-legion's next read of `POST /legion/v1/claims/approval` sees the approval (`internal/workflow/approval_route_paths_test.go`). A root's re-admission records the approved `spec` row that it deletes (`record.ClearedSpecApproval`), and the carry of a gate records the root whose document the gate holds (`record.HandedOverRoot.FromRoot`).
