What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The daemon publishes each change of what Dispatch observes as a state event on `notifications.legion.<token>.state`: one message for each transaction it committed, or consecutive messages split between events where a transaction's events pass 900 KB (`stateMessageBound` in `packages/daemon/internal/daemon/outbox.go`), its events in the daemon's own sequence (`legionStateMessage` in `packages/contracts`). The intake (`intake.go`, `Intake`, which `cmd/dispatch` starts whenever it has NATS) takes the messages from the held durable `legion-state-events` (`bus.DispatchLegionStateDurable`, through `delivery.NewHeldDurable`), so one process at a time applies them, and it runs each project's messages one at a time. For each message it writes, in one transaction, every value the message moved in `legion_observations`, one `legion_reads` row of kind `events` at the daemon's commit time, and the project's cursor in `legion_event_cursors`: the daemon's run and the last sequence applied. It reads a daemon's `GET /legion/v1/state` whole (`ReadWhole`, through `client.go`, held to `RequestTimeout`, 60 s, and `ResponseLimit`, 8 MiB, and sending no credential) only where the events cannot carry the state: a project with no cursor, or a cursor that follows another daemon, at each take-over and each write of its setting (`dispatch_legion_settings`, `SettingsChannel`); a boot event that does not follow the cursor or that applied a migration; a message past a gap the stream no longer holds; and a read owed since one failed, at most once a minute. No timer reads a daemon. A whole read runs on the project's own runner, so it never interleaves with the project's messages. It records how it went in `legion_reads` (kind `read`, with its reason) and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, all at one moment, 1 µs after the project's newest row where that is later than the read's time, and it sets the cursor to the state's own `daemon.stateSeq`, the sequence that snapshot reflects. Both writes keep the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the writes and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement. Both announce themselves on `dispatch_legion_state` (`StateChannel`) when they commit, which an open `/ws/live` `legion` view hears. After a batch, at most once an hour in each process, the intake prunes reads older than a week, keeping each project's newest. A read the daemon did not answer, or answered with another project's state, keeps the last good observations. A read whose state carries no `daemon.stateSeq`, a `stateSeq` of 0, or settings with no `dispatch_url` records its observations and is a failed read all the same, so the read stays owed. The board's header names the failure of each failed read, and goes on naming it over the batches applied after it while the read is owed. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the four Legion delivery metrics from the same records (`Read`, then `Compute`); no route serves them. The edges are the store's pool and the five tables its migrations create (`dispatch-store`); the held durable the intake runs under, and the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`); the bus client the intake connects with (`envoy-listener`, `internal/bus`); the generated subject of the state lane (`contracts`); the actor a setting records (`dispatch-model`); and the GitHub App client the metrics read merge times through (`dispatch-auth`).
