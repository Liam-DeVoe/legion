Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records. The largest package in the server (156 Go files beside their tests) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is a Go import as well as the wire contract. 36 of the package's files import `internal/contracts`, the Go package `bun run gen:go` writes from `packages/contracts`, for the headers, bounds, codes, subjects, the going stream's frame names and the tool specs' argument fields that the server and its clients must spell alike. The response shapes go the other way: `envoy-dispatch openapi` reflects this package's route table and the Go types of its rows into `packages/contracts/schemas/dispatch-openapi.json`, which `bun run gen:api` renders into `src/dispatch-api.generated.ts` for the web app. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

The related-item check of a write that asks a person a question offers more than one project's items. An ask create, a new decision block, and the POST form of `/api/v1/projects/{key}/related`, which `dispatch related` calls, also carry up to two answered questions of other projects (`other_projects`, read by `related_other_projects.go`). That leg searches by meaning alone, because the keyword leg weighs each word against the term statistics of one project. It starts as soon as the check holds its embedding, on a second connection mark the check takes before it opens the one-project read, and it reuses that embedding. The meaning stage then waits at most 300 ms for it, and ends the wait 25 ms before its own deadline. A leg that fails, that overruns that wait, or that got no connection leaves the one-project answer whole, records no reason and offers no item. A check that fell back to keywords offers none either. An issue create and the GET form of that route ask for none, so the dashboard's new-issue dialog draws the asking project's items alone. Each offer of an ask create is one `write_suggestions` row of role `other_project`, beside that check's `related` rows, and the outcome sweep resolves it like any other row. A new decision block's offers reach no row, because such a row is keyed by the ask the offer was made on and a block has none. `GET /api/v1/related-checks` answers `other_project_offers` beside the counts it reads from `related_checks`: the ask creates of the window that made such an offer, counted once each. The check answers no `decision` any more, and `persistSuggestions` writes no row of that role.

The live paths hold bounded state per reader. The event stream relay (`event_stream_relay.go`) is the live paths' one reader of the event log: its first subscriber starts a generation that listens on `dispatch_events` and reads each commit once, encoding each event's frame once for every subscriber, and the cancel of its last subscriber stops it at once, so a process nobody subscribes to holds no LISTEN connection of the relay's and the relay reads nothing. The events view of `GET /ws/live` (`live_events.go`) subscribes to it. A resume at or below the relay's head is replayed at most 256 events whose frames total at most 1 MiB, counted by rows; past either bound it is replayed nothing. Its `events_start` says `replay_complete: true` only when the replay is everything the page lacks, which includes a resume ahead of this process's relay but within the log; a page whose subscription starts without it refreshes what it shows. A subscription whose 64-slot relay subscription overflows catches up from the log within the same bounds and goes on; past them, or when the relay's generation ends (an event log reset, shutdown), it ends as `behind` and the page subscribes again. The delivery hub takes its events from the relay's feed (1,024 slots) and itself listens only on `delivery_changes` and `delivery_freshness`; it also stops with its last view, a closed feed makes it reload the open P0 issues and recompute every view, and an event that arrives during a view's read and touches the answer that read gives recomputes that view again. A comment's mentions are resolved in its request, up to 8 lookups at once, each bounded at 250 ms, so a listener that answers none delays a comment with up to 8 mentions by one 250 ms timeout and each further 8 mentions add one (ceil(k/8) timeouts for k mentions); the attempts commit pending with the comment, and the response returns them pending. The mention sender (`comment_mention_sender.go`) sends them after the response on one FIFO lane per recipient (the pinned session, else the target as written: `role:X` shares its holder's lane only when its lookup found the holder, and an unanswered `role:X` is keyed by its string, so two comments to one recipient can then arrive in either order), 8 lanes at once and at most 4,096 sends queued; once shutdown starts it queues nothing more (a refused send is logged at WARN), starts no queued send and gives the sends in flight 10 s. An attempt no sender finishes is the delivery sweep's (`delivery_sweep.go`, `resumeOwedDeliveries`): one process's maintenance loop, under the sweep's lease, sends once a minute every pending attempt that is the latest of its target, is claimed by nobody or by a claim that lapsed, and was created between a claim lease (one minute) and the duplicate window ago (`model.OwedMentionAttemptSQL`), whichever process left it, through the same claim; an attempt younger than the lease is left to the process that queued it, so the sweep never takes a live process's queue out of order. So the attempts a stopping process refused, left queued or could not queue for the bound are sent by a later pass once they have waited a lease (in a rolling update the successor is up before the old process stops), and a killed process's send in flight by the first pass after its claim lapses, within a minute and a sweep interval of its taking, under its own idempotency key, so a send that had landed is dropped as a repeat. The same pass settles, superseded, every pending attempt no sender holds that a later attempt of its mention has already delivered the comment in the place of (`settleSupersededMentions`), which nothing else binds to. Each pass reads the partial indexes `message_deliveries_pending` and `comment_deliveries_pending` (pending rows by `created_at`): with nothing owed it is one statement a minute that reads no row; no event can drive it, since a killed process sends no signal and a stopping one refuses its sends after its lifetime ends. Order holds within one process only: an attempt resumed after a crash or a handoff can arrive after later comments. A session a mention may reach also gets the new comment's own copy on the route, the claimant, an author or a follower route only by one rule the outbox applies when it publishes (`attempt.leftToMention` in `internal/dispatch/outbox`), keyed by the one session each attempt counts under (`model.MentionSession`: an unanswered `session:<id>` mention counts as `<id>`'s, and a route equal to an unanswered mention's target follows that target's attempts). What the attempt came to - sent, live, abandoned, or owed to the sweep, each a predicate over its row in `internal/dispatch/model`, all built from the sweep's own definition - decides the copy and which of the outbox, a sender's claim and the sweep acts on the attempt; a copy held back for a resumed mention is a `comment_fallback_copies` row, which the outbox's fallback pass publishes to its one destination only once the resend fails, never touching the event's own row. `publishFallbackCopies` in `internal/dispatch/outbox/mentions.go` is the protocol's one description. So a mentioned session loses no comment through a kill. The copy on the own topic of a session with a failed (or abandoned) attempt, and every fallback copy, carries that attempt's mention dedupe key, `agent.<session>.<comment>:<target>:<the mention's mode>` (`contracts.AgentSendDedupeKey` of `model.CommentMentionIdempotencyKey`, the lowest failed target's when there are several; the mode in it is the one the comment recorded on the mention and never an attempt's own, every attempt of one mention sending under that one key), in place of `dispatch-<event id>`, which every other destination carries and which stays its event id. So a send the killed process had handed the listener before it died, whose resend then fails for good (the listener down after the restart), is not shown twice: the host drops a frame whose named dedupe key it claimed within 72 hours, and the stream, whose MsgId is the dedupe key and the subject, also drops a second message with that key on that subject within its 72-hour duplicate window. A session no mention reached never claimed the key and is shown the copy. An unanswered `role:X` mention reached under any other string, and a `role:X` route whose own lookup went unanswered, name no session to compare, so that session can get both copies. An agent view (`live_agent.go`, `agent_stream.go`) queues at most 8 MiB of frames; past that it ends as `behind`. A page that stops reading meets the socket's own bounds first (#2449): the writer's 10 s write deadline (`liveSocketWriteWait`) ends the socket, which holds at most 16 of the hub's frames (`liveSocketQueue`) and 64 stream frames (`liveSocketStream`); the agent view's 8 MiB bounds only what it buffers while the socket writes slower than the session produces.

It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, the spent DPoP proofs, the command bar's answer runs past their window and its run records past their thirty days, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces any of them.

An access token the secrets broker issued is the one credential that proves a session of its own (`broker_token.go`), and it names either the person it acts for or a service: the fleet of a machine nobody has signed in on, or the service of a read entry. A machine's token that names no person reads everything its session may read, and `writeNeedsASignedInPerson` (`project_scope.go`) refuses its every write `403 SIGN_IN_REQUIRED` naming `agent-secrets login`: Dispatch records a write under the person who made it, and this credential names none. It is the outermost of the three checks `Register` wraps every mutating route in, before the project and session scopes, so such a caller is told it may write nothing at all rather than which project the write it tried belongs to. The credential-relay rows (`credential_requests.go`) carry the person's own sign-ins beside their machine logins — `GET /api/v1/signins` and `POST /api/v1/signins/{id}/revoke`, each naming the person from Dispatch's own session, so nobody reaches another's — and `GET /api/v1/credentials/capabilities`, which answers `{"machine_code_page": <bool>}` out of the broker's RFC 8414 metadata and, alone among these rows, answers rather than 404s for a Dispatch with no broker, since a 404 would leave the page unable to tell a deployment without a broker from a route it failed to reach.

A read-only broker token is the token the broker mints from a read entry: it holds the OAuth scope `read` alone and the project scope `none`, names a service and a fixed session, and names no person and no project. `brokerTokenActor` marks its credential `model.Credential.ReadOnly` and gives it no scope. It reaches only the routes `readScopeRoutes` lists beside `routeScopes` (`routes_table.go`), today `GET /api/v1/projects/{key}/architecture` alone, and `register` refuses to mount a list that names anything but a mounted GET row (`readRoutesNotMountedAsGET`). The gate `refuseReadOnlyToken` is the outermost check of every row and of `GET /ws/live` (`routeHandler`, `liveSocketHandler`). On every route the list does not name, it answers that token `403 READ_ONLY_TOKEN` with no `WWW-Authenticate` challenge, before the scope gate, the sign-in check, the `Idempotency-Key` and the handler. The route index and the OpenAPI document do not carry the list, and `/ws/doc/{room}`, which reads no broker token, answers that token `401`.

The command bar's answer path is the going routes (`going_routes.go`, with the record's reads and writes in `going.go`). `POST /api/v1/going/requests` records the question, the project it is asked of and the context chip (`{path, project, issue, block}`), answers `201` with the run, and then answers it in the background (`startGoingRun`), bounded by the 30-second `ends_at` the record holds. A run with a measured decision model (`Decider`, `going_decider.go`) first makes one `agentloop.Decide` call to its System One endpoint, bounded at one second. That call asks three questions (`goingDecide`, `going_decision.go`): which catalogue action the words ask for, chosen only among the actions the caller's credential may run, or `none`; whether the words are about the chip's item (`page`), items they name (`named`) or nothing; and chart or prose. The thresholds the run compares the confidences with are the model's entry in `going.DecisionRecord`, and this package holds no threshold of its own. The run then stores the `decision` frame: the two best actions, `act` (the first is at or above the action threshold and is not `dispatch_send_to_agent` or `dispatch_issue`, which always ask), the context, and the display, whose `chart` is true only at or above the chart-display threshold. A decision call that fails, or that names no action it was offered, gives no decision frame, and the answer runs as with no decision model. The answer itself is `going.Answerer.Run` (component `envoy`). The run gives it the offered actions with their argument schemas, the display, and the read tools its caller may call. After the text frames the run stores a `block` frame where the structured reply drew a block the words ask for, a `roster` frame `{age_ms, source}` where the answer read the roster, and, after a decision, the `proposal` frame (`goingPropose`). For each offered action the proposal holds one invocation for each item it changes, each held to the action's own schema, with a target filled from the chip only where the context is `page`, and at most one missing argument the bar asks the person for. An answer that came as prose writes no block and no arguments, and its actions are offered on what the chip fills. `POST /api/v1/going/requests/{id}/cancel` sets `going_requests.cancelled_at`. After that, `goingAppendEvent` stores no frame that does not end the stream, so the answer stops at its next delta on any pod; on the pod that runs the answer, the cancel function the server holds in `goingCancels` stops it at once. `GET /api/v1/going/capability` answers `{answer: {configured, model, blocks}, decision: {configured, model, reachable}, session, label}`, and names no endpoint and no credential.

The read tools of a run (`going_reads.go`) are reads this table serves, made in process through the functions those routes answer with, as the run's author: the roster of `GET /api/v1/agents` (`agentRows`), an issue's or a project's progress from `GET /api/v1/issues`, a project's architecture counts (`architectureTree`), the three delivery reads, and `GET /api/v1/projects/{key}/activity` (`project_activity.go`), which counts the events of a project's issues per ISO week and by kind over the last weeks (default 8, at most 52) and lists every week of the span, a week with no event as 0. A caller is offered a tool only where its credential may call every row the tool reads (`goingReadsFor`). A credential scoped to one project is offered no roster and no delivery read, and every other read is held to the run's project. `Register` refuses a table that does not serve a row a read tool names. The roster read waits out a `503 ENVOY_REFILLING` where the run keeps 5 s for its answer after the wait, and otherwise reads the sessions Dispatch's own rows name; the `roster` frame says which. A block's spec names one read, its arguments, its table and its fields, and never a number. The run parses the spec against its kind's schema, makes that read again as the author, and fills the block from the read's rows alone (`going_blocks.go`). It drops a block of a kind the words do not name, a chart the decision did not settle on, a read the run may not make, and a read that cannot fill the block, a chart of fewer than two points among them; the answer then stays prose and links.

The bar's operations are two routes. `POST /api/v1/going/runs/{id}/writes` (`going_writes.go`) runs one invocation of one offer of the run's proposal, with any arguments the person changed, the value of the missing argument, and `approved` (`auto`, `person` or `confirmed`). It performs the write in process as the caller: it calls the route table this server mounts (`server.inProcess`, behind `EnforceCookieOrigin`, the one cross-site check, which the router also wraps the whole server in) with only the caller's `Authorization`, `Cookie`, `Origin`, `Sec-Fetch-Site` and `Dispatch-Login` headers, and the trusted identity header on a deployment that names its people by one. So every check a route makes runs as on the caller's own request. Each catalogue row's translator (`going_translate.go`) does the work the `dispatch` command does before it sends, and refuses by name what it cannot send for a reason of its own; a call the bar can never send as written, which needs no read to tell, is refused before its translation (`goingUnsendable`, called by `GoingCaller.prepare`), and the proposal withholds it in the same words; the write's own check before it sends (`goingSendRefusal`) refuses, however the write came to run, an upload with content and no `force` under a name its owner holds a document of, naming the document and the name to write in the question to ask for its replacement (`goingUploadForceRefusal`, `goingUploadReplaceAdvice`, `400 GOING_ARGUMENTS`). Every `400 GOING_ARGUMENTS` answers the refusal's reason alone (`GoingArgumentError.Reason`), never the action's name before it, since the bar prints it on the line that names the write. The route reads the value before just before the write, in the same way, and records the write, refused or not, on the run's record, with the undo the row it went through states and how each request it sent went (`requests`: a reasoned close posts its reason as a message, then closes); an upload's value before is the document its name finds under the owner its route writes to (`goingRouteUploadOwner`). What a write that went through found and left is what its route answered its own transaction found and left, never a read on either side of it (`goingObserver.observe`): an update's `previous`, the issue it answers and, for a rank, the places `previous.rank` and `rank_place` (`issueUpdated`); an ask edit's `previous` and the ask (`askEdited`); a resolve's `previous` and the comment (`resolvedComment`); a claim's `previous_claim` and `claim` (`claimAnswer`); an upload's `previous_version`; a follow's change as its request's landing records it in its own transaction (`goingObserver.landed`); and for a document edit the reads before and after it held to the edit's `previous_token` and `token`, since the edit answers no content: a read after of another token is recorded `after_unread`, a read before of another token `before_unread`, its value before null. A write whose value after could not be read, or whose route's answer does not say what it found or whether it changed the claim, is recorded `after_unread`. Each invocation of a run is written once: the write first claims its invocation on the run's record, pending, in one statement that holds no lock and no connection past itself, so of two requests for one invocation one claims it. A request for an invocation whose write went through writes nothing and answers `200` with that write's line as the run recorded it; one for an invocation another request is writing answers `429 GOING_WRITE_IN_PROGRESS` with a `Retry-After`.

A request of a write has landed when its route's transaction committed, whatever status its answer carried (`going_landed.go`): each request the write sends carries a landing on its context (`goingLandings.on`), and `goingInProcess.Do` hands its route, in place of the writes route's own commit step, the step that records the request landed on the write's pending element of the run inside that route's own transaction (`goingLanding.step`, which reads whether the transaction wrote as `markRequestKeyCommitted` does), so the change and the record of its landing commit together or not at all; the write then reads that record back (`goingLandings.landed`), and never takes a landing from an answer. So a route that committed and then answered `5xx` - `createStoredMessage` when its delivery read fails, or any commit whose answer is lost - has landed and is never sent again, and a write whose every request landed went through, recorded `after_unread` where its last answer was no `2xx`. A write claimed longer ago than its request can still run and record what it did (`goingClaimBound`: the keyed handler's bound and the bookkeeping after it) is read for what it landed before anything else of the next request for its invocation runs. One whose every request it sends (`sends`, recorded before any is sent) landed went through: the press takes it over (`adoptGoingRunWrite`) and records it so, answering its line whatever the press asked, with nothing of it translated, read before, checked or sent again (`answerGoingWriteLanded`, `goingWriteClaim.landedWhole`), so a reasoned close whose close landed is never refused for the issue it closed, nor an upload without `force` for the document it made. One whose record names a request that landed, and not every one, is taken over, and once the press's call is translated it is compared with what the write landed (`goingStartsWith`): where the call sends those requests first it resumes the write after them, its read before and checks running for the requests that did not land, so a write whose process ended after its reason was posted closes and posts the reason once. A press refused before that comparison - by its session lookup, its translation or its encode - cannot tell the write's record from its own, so it writes nothing onto it and gives its claim back (`goingWriteClaim.giveBack`, `restoreGoingRunWrite`, which moves the claim back to the moment it held while it is still this press's), the write standing byte for byte as it was for the press that reaches the comparison; its refusal names only the landings whose method, path and body digest prove them its own requests (`goingResumeAfter`), so a translation's refusal of a press with that write's arguments names each request that write landed, once. One never planned (`sends` 0) - its process ended after its claim and before it sent anything, as the record proves, and its record names no request of its own, at most `inherited` copies of what an earlier write of the invocation landed, which that write's own record names - is taken over the same way and run whole as the press's own write, whatever its arguments (`goingWriteTakenOver`), as an undo never reached is made again; the takeover is the one statement that moves the claim while it is still past the bound, so of two presses taking it over at once one runs the write and the other reads the claim under way, `429 GOING_WRITE_IN_PROGRESS`. Only one planned whose record names no request landed answers `409 GOING_WRITE_UNSETTLED`, since its request may have run, and is never written again. A taken-over write's landings are never rewritten: where the press that took it over does not send first what it landed (its arguments changed), the write is recorded as it stands (`settleGoingTakenOver`), refused `409 GOING_WRITE_UNSETTLED` naming what it landed itself, never a request it holds `inherited` from an earlier write it resumes after (`goingInherited`: the copy a claim starts with and the copies its plan takes), after which the press claims a write of its own. A write taken over keeps the item, fields, value before, read-before token and undo it recorded (`claimGoingWrite`), so a refusal after its comparison and before anything was read records them still. A write of several requests is one write to its `Idempotency-Key`: none of its requests marks the key committed, and the write's record marks it once the write reaches a final outcome. A refusal is recorded under `store.WithoutBeforeCommit`, with what landed before it named in its answer once (`goingRefusal.after`, which leaves a refusal that already names them as it is); a refusal the keyed layer keeps an answer for (a `4xx` but `401`, `408`, `429`) is the write's final answer, replayed to a retry under the key however much of the write landed, and one it keeps none for (`5xx`, `401`, `408`, `429`) by a route that did not commit leaves the key open. Every later write of the invocation that runs - a retry under the key, or a new press, the bar's own retry or another tab under a key of its own - resumes after the requests its own call landed in the invocation's writes (`goingResumeAfter`: of those writes, newest first, the one whose landed requests are the call's own, by method, path and body from its first, for the most of them), which the claim records, with how many requests the call sends, its item and its value before, before anything is sent (`goingLandings.plan`), and sends none of them again (`GoingCaller.send`); its claim holds only while the invocation's latest write is the one it read (`claimGoingRunWrite`), and an earlier write, once recorded, never changes, so a write another request recorded between the read and the claim is read again first. A translation's own refusal words only what of the call was not sent, deciding by the call's own requests whether it resumes after one an earlier write landed (`goingCallInput.resumes`). A send to an agent's recipient the roster does not list - it lists running sessions alone - is looked up by its id through the Envoy listener (`goingReader.recipient`, `server.goingKnownSession`), as the send's own route looks up its target (`resolveDeliveryTarget`): a session that has stopped reaches the route, which stores the message and records its attempt `queued`, one the listener knows as gone is stored with its attempt `failed`, a name the listener knows no session by keeps the roster's `404 GOING_SESSION_NOT_FOUND`, and a listener that cannot be asked is `503 ENVOY_UNAVAILABLE`, with nothing written. An upload with `force` is held to the rule its offer is held to whenever it runs, whoever approved it: where its read before, made under the owner its route writes to as the store stands then (`uploadedOver`), finds a document the person did not ask for (`goingUploadAskedFor`: the upload's name is not the name that document is stored under, or the words do not write that name), it is refused `409 GOING_NOT_PROPOSED` in the words a proposal made now would withhold it with (`goingUploadOverRefusal`, `goingUploadWithheldReason`), with nothing written, so a document made between the proposal and the pick, and one the proposal could not read the owner of, are no more written over by a pick than by a write sent at once. It refuses `auto` with `409 GOING_APPROVAL_REQUIRED` for the two writes that always ask and for any action but the one the decision chose at or above the action threshold, with `409 GOING_NOT_AUTOMATIC` for an invocation the proposal did not mark automatic (`going_named.go`: every item it names is the chip's or a reference the person's own typed words write, every route or assignee it sets the words name or the issue already holds, an upload's name is one its owner holds no document of, or the name the document it finds is stored under, which the words write (`goingUploadAskedFor`), never that document's slug, or, where the owner cannot be read, one the words write, and every argument is one the catalogue's classes hold), for one sent with arguments replacing its own, and for an upload whose route names no owner the write can read (`ownerUnnamed`) and whose name the words do not write (`goingUploadsOver`, read once the write's row is chosen, with nothing written; the proposal's read is the offer's hint), and with `409 GOING_CONFIRMATION_REQUIRED` while the caller's `confirm_writes` is on. `GET` and `PUT /api/v1/me/going/settings` (`going_settings.go`) read and write that setting, which is the person's own, keyed by canonical login, and false until they set it.

The refusals of `auto` (`goingAutoRefusal`) reach the person in the bar's panel, on the line that names the write, and only where what the page holds disagrees with the server - a copy of `confirm_writes` read before the person turned it on elsewhere, a build of the bar older than the run's record - so each says what happened and what that person does there, and names no tool and no value of `approved`: a write that runs only when the person picks it says to ask again and pick it, which a new run offers as a row they pick (`goingPickToRunAdvice`); one whose arguments replace its own says to ask again with the change written in the question; and `409 GOING_CONFIRMATION_REQUIRED` says to submit again to confirm it, since the bar reads the setting again on that refusal and its next submit asks first (`dispatch-web.md`).

What a write taken over after every request of it landed found and left is what its last request's route recorded beside that request's landing, in the transaction of the change: every route whose answer says what it found and left hands that answer to the landing just before its commit (`goingRecordAnswer`, the request's `goingAnswerSink`), and the landing step records it (`goingWriteRequest.answer`, its status in the outcome) in the same statement, so the change and its values commit together or not at all and no death falls between them. The routes that do so are the issue update (`issueUpdated`), the claim and the release (`claimAnswer`, in `claimWrite`), the issue create (`201` with the issue, and `200` with the one an external reference names), the ask edit (`askEdited`), the ask open, the comment resolve (`resolvedComment`), the follow and the unfollow (`204`: the landing is the change), the document edits (`token`, `previous_token`) and the uploads (`artifactUploadResponse`), the approval request (`opened`, `201` or `200`), and a send to an agent (the message it stored, by id: `POST /api/v1/agents/{session_id}/messages`, in `createStoredMessage`). The takeover reads them as `observe` reads the answer (`goingObserver.recorded`, the call's row named by the recorded request itself, `goingRecordedCall`), never a read made after another writer may have moved the item; a document edit's value after is the document read then only where it holds the `token` the edit recorded, and its value before the read before (whose token the claim recorded, `before_token`) only where that token is the recorded `previous_token`. A landed send to an agent whose line holds no delivery - its route's answer went unread, answered `5xx` after its commit or lost with the process making it - has its message's last delivery attempt read by that id (`goingWriteClaim.sentDelivery`), a read for the line alone; where none can be read the line carries no `delivery`, which the bar reads as the words stored and their delivery unknown. A write whose last route recorded no values, or values that do not say what it left, is recorded `after_unread` (`goingLandedWhileDown`), and its undo says so; its line keeps why, as a write read at once keeps it: a refusal of what that needed (a document another writer edited since) in the refusal's words, and anything else - a record naming nothing its route answered, a row the catalogue no longer holds, a read that failed - as the server's own failure, logged at `Error` with its cause. A recorded write or undo keeps none of these answers (`goingWithoutAnswers`).

A route's bookkeeping that commits before the route can refuse is no landing of the request: it commits outside the request's commit step (`store.WithoutBeforeCommit`), as the issue close's settlement (`settleIssueBeforeClose`), the conditional edit queue (`docs.Service.admitConditionalEdit`) and an architecture sync's failure record and re-resolved installation (`architecture.Importer.recordFailure`, `Importer.resolve`) do, so a one-source sync refused `409 SOURCE_ACCESS` is the write's refusal, and a keyed sync whose import never ran marks no key committed.

An upload under the name of a document its owner already holds, as the proposal reads the store (`goingHolds.document`, which answers that document's stored name and slug), is offered only where it carries `force`, the answer wrote the name the document is stored under, its file name, and the person's own words write that name, as a whole word and whatever its case (`goingUploadAskedFor`, `goingWordsName`), and withheld otherwise (`goingUploadWithheld`): without `force` every write of it is refused and no control of the bar sets `force`, and with `force` a pick replaces the document's text, which nothing the bar shows says unless the person asked for that document. An upload that finds the document by its slug is withheld whatever the words, its `withheld` naming the stored name the person would have to write, and the stored name without its extension counts for nothing: an issue's own spec is stored as `spec.md` under the slug `spec`, so "replace spec.md with this" offers an upload named `spec.md`, while "replace the spec with this" and "add a note to the spec" offer none, named `spec` or `spec.md`; "add a note" writes the stem of `note.md`, a word people type for every other reason. The proposal's mark of an upload that runs at once (`goingNamed.uploads`) and every write of an upload with `force`, however it came to run (`goingUploadOverRefusal`), hold an upload over a held document to the same rule, each against the store as it stands when it reads it, so the offer is the only promise the bar makes and the write keeps it; `goingUploadsOver` decides only an upload sent at once whose route names no owner the write can read, which it holds back for the person to pick. A pick of such an offer is made, where the document it was offered over is still the one the read before the write finds. The offer carries why in `withheld` (`goingOffer.Withheld`, `GoingOffer.withheld`), which the bar shows beside whatever of the action it offered, and where it offered none; the write's own refusal carries the same words (`goingUploadWithheldReason`), or, where the name is the one the person filled in for an upload whose answer left it out, the words of a filled-in name (`goingUploadFilledNameReason`): a name filled into the one argument the invocation was missing asks for a document of it to be made, not for the one it finds to be written over, and names the stored name to write in the question. Every one of these reasons is worded for the person reading the bar's panel (`goingUploadReplaceAdvice`): it says what that person can do there - write the document's stored name in the question, or open the document and edit it there - and names no tool, no `dispatch` command and no flag, none of which that person holds. An upload the proposal could not read the owner of is offered, and held at write time to the force check, to that rule, and, in the store, to a create alone: every upload carries that condition to its route on the request's context (`goingUploadCondition`, `goingCondition.ExpectNew`) - one with `force` too, unless its read before found the document of its name, one the words ask for, whose next version it then writes with no condition (`goingUploadWritesOver`, settled before the plan, the call's requests encoded again since the condition is part of each request's digest) - and the upload routes refuse it under the owner's lock where the owner holds the name by then (`storeArtifact`, `409 DOCUMENT_EXISTS`), so a document another writer makes between the write's read and its upload is never written over, whatever the upload's `force`. The upload routes take no version or token of the document an upload writes over, only the SHA-256 of the markdown it must hold (`ExpectSHA256`), which the read before does not read and a file cannot carry, so an upload with `force` over the document its read before found is held to nothing more. An expected content (`ExpectSHA256`) is a document's alone: an upload of a file carrying one is refused `500 GOING_CONDITION_MISSING` before anything is written, so a write back never becomes an unconditional write of a file.

A call the bar can never send as written is withheld the same way, whatever the words (`goingUnsendable`): a comment, a question or a message carrying picture files, which the `dispatch` command reads off the machine it runs on; a comment, a suggestion or a document edit whose place a `dispatch://` reference gives, where the bar places a write by issue, project and document; an upload of a file, or with no text; an update with a closing `reason` that does not mark the issue `done`; and a sync of a repository not written as `owner/name`. None needs a read, so the proposal decides it as `GoingCaller.prepare` does, in one function, and its `withheld` is the very reason a write of it is refused with, `400 GOING_ARGUMENTS`: what the bar cannot send and what the person can do there - ask again for the words alone, naming the issue or the document, or with the text to upload in the question - naming no tool, no argument, no command line and no flag. An ask's `ref` is none of these: the question carries it as a line of its own. A translation's refusal that needs no argument but the caller's own session - a handoff or a reply to a delivery by a caller acting as no session - is the translator's own (`goingUntranslatable`), since the bar never offers either row to a person's browser (`GoingRoute.runnableBy`).

A landing is recorded at its request's own index (`goingPaddedRequests`), and once a request another of the write is sent after is answered, the writes route adds to its landing the status it was answered and the item it made (`goingLandings.answered`, outside every commit step), so a write taken over after its process ended names them; one whose every request landed in an earlier attempt that ended before its last answer was read is answered the status its last route recorded beside its landing, else `200`, the writes route's own. A landing counts only for the very request it records, by method, path and the SHA-256 of its body and of the condition it carries on its context (`goingSend.digest`, `goingSameSend`, `goingLandedRead`), and every landing names that digest, so one that names none is no landing of any request: a press that changes a close's reason posts its own, and one whose changed arguments send another request than an earlier attempt at an index resumes nothing from there, so a refused request is never read as landed by another request's record.

`POST /api/v1/going/runs/{id}/undo` (`going_undo.go`) undoes every write of the run that went through and that no undo settled, newest first, in process as the caller, by the undo the catalogue row it went through states (`GoingUndo`, as the write's record keeps it): `write_back` writes the value before back, `reverse` runs the write's reverse route, `close_created` posts the reason on an issue the turn created and closes it, and `trace` records the undo and erases nothing. Each request an undo sends records its landing in its route's own transaction, on the undo's pending element, at its own index, as a write's does: the pending undo holds from its claim the requests an earlier undo of its write landed (`claimGoingRunUndos`), and a landing past the end of the requests is padded to its index (`goingPaddedRequests`). A field another writer changed since the write is left as it is, refused `409 GOING_UNDO_CHANGED`, and the rest of the turn is undone. A refused field's message says what became of it without naming the field, which the line holds beside it and the bar prints before it, and the line's outcome names each field it speaks for (`goingFieldChange`). The values an undo compares and puts back are the ones the write's record holds, which are what the write's own route answered its transaction found and left (see the writes route above), never a read on either side of the write. Every undo that writes a value back is a compare-and-set the route it writes through decides under the lock that write takes, never a read and then a write, and each is one of the bar's in-process conditions (`goingCondition`, `going_conditions.go`): the in-process caller carries it to the route on the request's context and never in a body, so no client off the network can send one and no build can drop one from a body it does not declare (`decodeJSON`), and a body naming one of the old members (`expect`, `expect_sha256`, `expect_new`, `expect_holder`, `expect_unclaimed`, `expect_resolved_at`) is answered as one naming nothing. A claim is released only while the holder it left still holds it (`ExpectHolder`), a release is taken back only for the holder its route answered it released (`previous_claim`), where that holder is the one the undo's own claim is recorded as (`goingUndoer.claimant`: the session the caller's credential proved, else the person), and only while nobody holds the issue (`ExpectUnclaimed`), both refused `409 CLAIM_HOLDER_CHANGED` otherwise; an issue's fields and rank are written back expecting what the turn left (`Expect`, `issueExpectationRefusal`, refused `409 ISSUE_CHANGED`), an ask's text the same (`Expect`, `askExpectationRefusal`, `409 ASK_CHANGED`), a document's content expecting the markdown the turn left (`ExpectSHA256`, `docs.Service.ReplaceTextExpecting`, `409 DOCUMENT_CHANGED`), a created issue is closed only while it holds the status the turn left it in, the one its write recorded in its value after (read before the reason is posted, nothing posted where it moved, and the close's `Expect`, `409 ISSUE_CHANGED`; a record that names no status holds none to expect and is the server's own failure, nothing posted or closed), and a resolved thread is reopened expecting the resolution the turn left (`ExpectResolvedAt`, `409 COMMENT_CHANGED`); each of those refusals is the undo's `409 GOING_UNDO_CHANGED`, and another writer's change between the undo's read and its write is kept. Every request of an undo that writes a value back is marked as a write back (`goingCondition.WriteBack`), and a route that takes a condition refuses a write back carrying none it decides - none, an empty one, or one that leaves a field it writes unexpected - `500 GOING_CONDITION_MISSING`, with nothing written (`goingCondition.writeBackRefusal`), which leaves the write undoable; every other request carries no mark and is answered as before. The answers the undo reads (`previous`, `rank_place`, `previous_token`, `previous_version`, `previous_claim`, `claim_changed`, `opened`) stay on every caller's answer. A request the bar sends in-process refuses a body member or an upload's multipart field its route does not declare, `400 INVALID_JSON` naming it (`judgeUndeclaredMembers`, `undeclaredUploadFields`), since the bar and the route are one build. A retraction resolves an ask only while it is open (`transitionAskTx`), decided under its route's lock already and answered as that route refuses it; a follow and an unfollow write the one boolean the turn changed, so writing it back over another writer's change leaves the value that writer left. A release of any other holder's claim - a session's the person released, another person's, or the person's own undone through a credential bound to a session - is refused `409 GOING_UNDO_NOT_CALLERS_CLAIM` naming that holder, settled, with nothing written (`goingUndoer.claimsAs`): the bar cannot claim for them, and claiming as the caller would give the caller a claim it never held. A claim, a release and an approval request are undone by what their route answered they did, not by the reads around them, which another writer may overtake: the claim routes answer `claim_changed` and `previous_claim` (`claimAnswer`), recorded `unchanged` and as the value before on the write, and the approval request route answers `opened` (`approvalRequestResponse`), so a claim of an issue the caller already held, a release of one nobody held and a request that renewed an ask already open are undone by nothing. A write recorded `after_unread` is refused `409 GOING_UNDO_AFTER_UNREAD`, and one recorded `before_unread` `409 GOING_UNDO_BEFORE_UNREAD`, by every undo but a trace, with nothing undone; the `after_unread` line says why in the write's own words - for a takeover, that the write landed while the process making it was down (`goingLandedWhileDown`) - and that the person changes the item by hand instead. The undo claims every write it is about to undo on the run's record, pending, in one statement before it undoes any, which holds only while the run's undos are the ones it read (`claimGoingRunUndos`), so a second undo of the run while one is under way answers `429 GOING_UNDO_IN_PROGRESS`; an undo it made and could not record keeps its claim, as a write does. A pending undo's claim is marked with how many requests it sends just before the first is sent (`sends`, `goingLandings.reach`), as a write's plan records its own, and with it, for a write back, each field the write back leaves as another writer left it, naming what changed (`fields`), which none of its requests sends. Once a pending undo is older than `goingClaimBound`, the next undo reads what it landed before anything else (`goingUndoTakeOver`), as a write taken over does: one reached (`sends` marked) whose record names no request it landed is answered `409 GOING_UNDO_UNSETTLED` and never claimed or undone again, since that request may have run; every other is taken over in the same statement as the next undo's claim, its claim moved to that undo's moment with its landings standing - one that landed every request it sends is recorded as it landed with nothing sent again, each field from what that undo proved of it, never from the whole (`goingUndoLandedLine`, `goingUndoWriteBackLanded`): a write back's field its claim marked left is refused naming what changed, `409 GOING_UNDO_CHANGED`, as the live undo refuses it, one its PATCH's route answered it wrote (`previous`, recorded beside the landing) was put back, and one neither says is refused for the person to read, `409 GOING_UNDO_UNSETTLED`, never put back, where a recorded answer that is missing, does not decode or holds no `previous` is also the server's own failure, logged at `Error` naming the run, the write and its cause, as the write side logs a record that names nothing its route answered; a write's own record of what it left that does not decode, or that names no field, fails closed the same way (`goingUndoWriteBackUnread`): every field that write recorded changing is answered `409 GOING_UNDO_UNSETTLED`, never done with no field at all, and the failure is logged at `Error` too; one that landed some is resumed after them (a created issue's close after its reason), and one never reached, which made nothing, is made now. A taken-over undo the handler does not reach keeps its claim and is taken over again past the bound; the claims it made afresh and did not reach are given up as before. `GET /api/v1/me/going-runs?undoable=true` reads a run so too (`goingRunUndoable`): a pending undo past the bound holds its write only where it was reached and landed nothing.

The one undo that sends more than one request, `close_created` (`goingUndoer.closeCreated`), records how each went on the run's undo (`requests`), as a write does. Where its reason landed and its close was refused, its line names the reason it left posted, as this undo's own earlier request (`goingRefusal.after`, which names the write or the undo that sent it); where the close was refused for a cause that leaves the write undoable (`5xx`, `408`, `429`), the next undo of that write, under whatever key, resumes at the close (`goingUndoLandedBefore`) and posts no second reason, and a resumed close that committed is recorded done whatever it answered; a final refusal settles the write as before. Every refusal of a resumed undo before its close is sent - the issue closed or moved since, a record that does not say the status the issue was left in, a read that failed - names the reason an earlier undo posted, which stands, and keeps it in the undo's requests, so a later undo still resumes after it. A create its route answered `200` made nothing - it named an external reference Dispatch already held an issue for (`respondWithExistingExternalIssue`), the route's `201` being the answer of an issue it made - so the write records it `unchanged` (`goingObserver.observe` reads the status) and its undo is answered done with nothing read, posted or closed: that issue is not the turn's.

The run record is the `going_runs` row a run keeps under its going request's id (`going_runs.go`), and only a credential that acts as a person keeps one. The run writes the row as it starts and fills it as it goes: the words, the chip, the hits, the decision, the proposal, `structured_output` and `finished_at`. Each write and each undo is first claimed on the row, a pending element appended in one statement, and then recorded in that element's place in another, once it went through or was refused; a claim whose request made nothing is taken off instead. A run that was cancelled or abandoned keeps what it stored and reads unfinished. `GET /api/v1/me/going-runs` answers the caller's own runs of the last thirty days, newest first, with `?issue=`, `?q=` and `?undoable=true`, which is how the bar's undo key finds the newest turn from any page. The maintenance sweep deletes a row past thirty days (`sweepGoingRuns`), and the writes and undo routes answer `404 GOING_RUN_NOT_FOUND` for a run older than that, for a run that is another caller's, and for a run the record does not hold.

A broker token that names a person under the person project scope, which is what a person's `agent-secrets login` sign-in trades for, from the Go helper and from every TypeScript session client alike, gets the `person` and `approve` scopes (`brokerTokenActor`), so it may record a review in that person's name. Two routes record that review (`reviews.go`, both through `recordArtifactReview`). `POST /api/v1/artifacts/{id}/reviews` takes `{state, reason?}` and records the version the review would record whichever it is: the version the open approval request names for the document, else the latest settled version; it is the web app's call. `POST /api/v1/artifacts/{id}/versions/{number}/reviews` takes the same body, and `{number}` is the version the caller read: when the review would record another version the route answers `409 REVIEW_VERSION_MOVED`, naming the version it would record, before it answers the request or writes anything, and a `{number}` that is not an integer from 1 is `400 INVALID_REVIEW`. The guard is a route rather than a body member because a route ignores a member it does not declare, so a build without it answers no route rather than recording a version it chooses. `dispatch review` sends only the versioned route. The going catalogue (`going_catalogue.go`) gives `dispatch_review` no row, so the loop that proposes operations on the graph never proposes an approval in a person's name, and both review routes stay in `goingMutatingRoutesWithNoTool`.

A broker token carries a list of projects (`brokertoken.Caller.Projects`). Only a token an operator's entry mapped, under the named project scope with its one project, sets `Actor.Project`, the one project its writes are held to (`project_scope.go`); a person token's list, the projects its trade named and Dispatch said its person sees, limits no write at this release, so such a token writes wherever its person may, as one naming no project does (`broker_token.go`).
