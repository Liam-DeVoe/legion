Stages 1 and 2 on `main` provide Postgres migrations and boot history (`internal/store`), the local daemon registry, durable role claims, and pending task delivery (`internal/registry`). Stage 3 (LEGION-219) plans the per-issue record, admission slots, phase and gate facts, transactional outbox, and `internal/projection`; the coordinator never mirrors Dispatch or GitHub.

The transactional outbox runs an issue's rows on four lanes side by side: lifecycle, board, role message and claim (`record.OutboxLane`, run by `internal/daemon`'s lanes). The daemon's state events run on a fifth lane, `state`, which is a project's lane and not an issue's (dispatch://INFRA-3931). Every row of its three kinds, `state_change`, `state_admission` and `state_boot`, carries the bare Dispatch project key in `outbox.issue`, so a project has exactly one state lane. Each such row takes its sequence and its time when its transaction commits: a deferred constraint trigger of migration `20261118164019_state_events` steps the project's `state_publication` counter and writes `state_seq`, `state_at` and `state_tx` onto the row. So the sequence follows commit order and has no gap, every row of one transaction has the same time, and a transaction that rolls back leaves no row and no step. The lane publishes the rows strictly in sequence order (`outboxInOrder` in `internal/record`), and the rows of one committed transaction go out together as one message on `notifications.legion.<token>.state`, or as consecutive messages split between events where they pass 900 KB (`stateMessageBound` in `internal/daemon/outbox.go`). A row whose publish fails holds every later state row of its project until it is published. A row the listener refuses for good is dropped with an ERROR line instead, and Dispatch reads the whole state at the gap it leaves. `state_admission_blocks` keeps the admission block the daemon last wrote, so a pass that leaves the block as it was writes no row. The state route reads `state_publication.last_seq` in the snapshot it serves and serves it as `daemon.stateSeq`: every state event at or below it is in that snapshot, and none above it.

The issue record holds no experiment answer of its own: what each unit was drawn for is a row of `experiment_assignments` (migration `20261111045636_experiment_assignments`), keyed by the issue key and the experiment's name, carrying the unit the draw covers (`tree` or `issue`, the two words the loader takes), the arm, the mode in force at the draw, the instant, and the carried mark. The row is written once and never updated, as the draw it records is made once: the primary key is what makes that true in the schema, since both writers insert `on conflict (issue_key, experiment) do nothing`, so an experiment a unit has been running under keeps the arm, the mode and the instant it was drawn with whatever the project's file says by then, and a re-admission, a new generation and `ClearTreeGeneration`, which touch the issue row alone, keep what was drawn. `record.Store.PutAssignments` is the draw's write, made by every path that opens a unit in that path's own transaction, and it selects from the issue's own record: a key the daemon holds no record of — an operator's spawn, whose tree's root it never recorded — writes no row and raises nothing, where the row's cascading foreign key would otherwise fail that admission. `CarryAssignments` is the hand-over's write: every tree-unit row of the tree a child left is copied onto the child with its arm, its mode and its instant verbatim and the carried mark set, so the work goes on running under those arms; then each experiment declared at the hand-over lands at no variant, no mode and no instant under the same write-once insert, so it settles exactly the experiments the copy left unwritten, and the child is drawn for by nothing later. Only the tree rows are copied, an issue row of the old root being that one issue's own answer. The empty variant is the record's way of saying no arm, which the two columns beside it tell apart: an experiment at mode off draws for no unit and records the mode `off` with the instant of the draw, while a settled hand-over records neither. A unit opened before an experiment was declared holds no row for it and runs in no arm of it. The four `issues.memory_*` columns that `20261104073148_issue_memory_group` and `20261104153554_issue_memory_carried` added stay in the schema, are written by nothing from this release on, and are read by this release's code only through the migration's back-fill and by the documented copy by hand; `20261111045636` back-filled every root holding a draw (`memory_drawn_at` not null) or the carried mark into one `memory` row of unit `tree`, so no tree drawn before the deploy lost its exposure, and a later release drops them.
